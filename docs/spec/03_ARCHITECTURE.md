# 架构说明

> **文档状态**：`evolving` · 最后审核：2026-04-18 · 已按当前实际部署与默认运行链回写；正式业务真相仍以 Java 为主，默认数据基线为 PostgreSQL。
>

## 1. 上下文架构（文字图）
- 用户通过浏览器访问系统。
- 浏览器访问 `Caddy`。
- `Caddy` 路由到：
  - `React 前端`
  - `Java 后端 API`（`/api/v1/**`）
  - 可选 `Python Live bridge`（`/ai/interview/live/**`，仅 AI 面试 `live` 测试模式）
- Java 后端内部包含：
  - `AI 模块`（多模型路由、成本控制、用户分级配额）
  - `内容治理模块`（输入/输出审查、举报处理、敏感词与策略）
  - `学生画像 / 内容推荐模块`（本地规则画像 + Embedding 召回 + 内容推荐重排 + 推荐运行日志）
  - `PostgreSQL`、`Redis`、`MinIO` 访问
- Java 后端通过 AI 模块直接访问外部 LLM/STT/TTS 供应商。
- Java 后端直接处理支付宝沙箱回调。

## 2. 容器级架构
### 2.1 前端容器（web）
职责：
- 多角色界面渲染（React + TypeScript + Vite，混合使用 Ant Design、Tailwind CSS 与定制动效/布局组件）。
- 调用后端 API，处理 JWT。
- C 端：展示 AI 结果、社区、订单支付、成长体系等面向用户的页面。
- B 端：展示管理后台页面（内容治理、AI 配置、日志审计）。
- 路由级 Layout 区分学生/导师/企业/管理员工作区，并通过代码分割控制体积。

### 2.2 Java 后端容器（server-java）
职责：
- 业务真相与权限控制。
- 状态机和事务控制。
- 订单支付、社区成长、审计日志。
- 内容审查与举报治理（统一审查引擎 + 运营后台）。
- 统一通知模块（`notification_events`、`notifications`、`notification_dispatch_jobs`、`notification_dispatch_attempts`、`notification_preferences`、WebSocket ticket 与渠道派发）。
- 导师推荐模块：
  - 学生画像真相层以本地规则和结构化证据聚合为主。
  - 学生推荐快照 / 导师推荐快照持久化。
  - 本地可替换 embedding 向量生成与相似度召回。
  - 基于内容推荐和 frozen 导师广场规则的 100 分制重排。
  - 推荐运行留痕（run + event），便于解释与答辩展示。
  - 当前版本不把协同过滤作为主实现方向。
- **AI 模块**（集成在后端内部，不独立部署）：
  - 统一 OpenAI 兼容协议。
  - 多模型路由与回退。
  - Prompt 模板注入与版本化。
  - 超时/重试/熔断（Resilience4j）。
  - 调用日志与成本追踪。
  - 用户分级配额与积分扣减。

### 2.2.1 Python Live bridge（`apps/interview-live-python`，可选）
职责：
- 仅承接 AI 面试 `live` 测试模式的浏览器 WebSocket 连接。
- 把浏览器上传的 PCM 音频块与文本输入桥接到 Gemini Live。
- 把模型音频、输入/输出实时字幕、token 用量与续接信号回推浏览器。
- 默认暴露：
  - `WS /ai/interview/live/ws`
  - `GET /ai/interview/live/healthz`

边界：
- 该服务不持久化面试业务真相，不直接写 PostgreSQL/Redis。
- 面试会话、积分/配额预留、历史消息、总结报告、通知与复盘中心仍由 Java 后端负责。
- `live` 结束后由前端调用 Java 正式接口 `POST /api/v1/ai/interview/sessions/{sessionId}/live-transcript` 导回 transcript，再继续走 `/summary`。

### 2.3 基础设施容器
- `postgres`：事务数据主库。
- `redis`：缓存、锁、限流计数、AI 配额计数、举报频控计数。
- `minio`：音频与附件对象存储。
- `caddy`：反向代理、HTTPS 与统一公网入口。

当前补充说明：
- 截至 2026-03-31，本轮 Redis 四十条最小落地点已全部完成，当前 Redis 专题进入“已落地、待后续增量需求触发新任务”的收口状态。
- AI 运行时与异步链路当前已落地：AI 配额日用量、分钟级 Redis 滑动窗口限流、AI 面试创建短 TTL 防重复提交、AI 面试会话级 TTS 临时缓存，以及 AI 异步任务 worker 的 ready queue / lease / retry schedule 协调态均已接入 Redis；`ai_async_task_jobs` 与事件表仍作为最终业务真相。
- 通知在线链路 / 派发协调当前已落地：Redis 已承接用户在线索引、session 映射、跨实例在线判断、基于 Pub/Sub 的跨实例真实 WebSocket 转发，以及通知派发 worker 的 ready queue / lease / retry / ACK guard；通知收件箱与派发记录仍保留在 PostgreSQL 作为最终业务真相。
- 支付防重当前已落地：咨询支付回调、主动关单与退款均已接入 Redis 短 TTL done key + lock key 双 key 防重；数据库支付记录唯一键仍作为最终业务真相与并发兜底。

补充规则：
- 订单、支付、退款、积分账本、通知收件箱、AI 历史、咨询消息、认证原始提交、审计日志等业务事实数据，不能以 Redis 作为主存。
- Redis 中的数据默认应满足“可丢失、可重建、可过期、可回源”至少其一。
- 旁路缓存优先采用“短 TTL + 业务写入后精确失效”，避免维护大范围复杂双写。

## 3. 关键时序
### 3.1 AI 调用时序
1. 前端调用后端 AI 接口。
2. 后端鉴权与参数校验。
3. AI 模块识别用户等级（FREE/PREMIUM）。
4. 检查每日免费额度；超出则检查积分余额并扣减。
5. 按 `taskType + tier` 路由模型并调用供应商（WebClient）。
6. 记录 token 用量、预估费用、调用日志。
7. 持久化结果后返回统一响应体。

### 3.2 支付回调时序
1. 学生创建订单并拉起支付。
2. 支付成功后第三方回调后端。
3. 后端验签、验金额、验幂等。
4. 事务内更新支付与订单状态。
5. 写审计日志并返回确认。

### 3.3 咨询消息时序
1. 学生发起付费问题。
2. 导师在已支付订单内回复。
3. 订单状态从 `PAID` 到 `ANSWERED`。
4. 完成条件满足后置 `CLOSED`。

### 3.4 SSE 流式输出时序
1. 前端请求 AI 流式接口（`/stream`）。
2. 后端创建 `SseEmitter`，异步调用 AI 模块。
3. AI 模块通过流式 HTTP 接收供应商响应，每收到一个 token 即通过 SSE 推送给前端。
4. 全部 token 接收完毕后发送 `done` 事件，包含 `aiMeta`。
5. 记录调用日志与 token 用量。

### 3.4.1 AI 面试 Gemini Live 测试模式时序
1. 前端先调用 `POST /api/v1/ai/interview/sessions`，继续传 `mode=INTERVIEW_TEXT`，但在 `sessionContext.answerMode` 中标记 `LIVE`。
2. Java 后端完成积分/配额预留并创建占位会话；当前不生成 opening question，而是返回空 `firstQuestion`。
3. 浏览器连接 `WS /ai/interview/live/ws` 到独立 Python bridge；bridge 再与 Gemini Live 建立实时语音会话。
4. 浏览器在会话过程中持续接收模型音频、实时字幕、token 统计和断线续接信号；该阶段不直接写正式面试消息表。
5. 用户结束 `live` 后，前端把整理好的 `USER / ASSISTANT` transcript 调用 `POST /api/v1/ai/interview/sessions/{sessionId}/live-transcript` 导回 Java。
6. 前端随后调用 `POST /api/v1/ai/interview/sessions/{sessionId}/summary` 生成正式复盘；总结、通知与 `/ai/history` 记录继续按 Java 主链路留痕。

### 3.5 通知时序
1. 业务事件发生（如 AI 简历任务完成、导师回复、支付/售后变更、企业审核、认证审核、系统公告）。
2. 统一通知发布服务先写 `notification_events` 留痕与去重，再为目标用户写入 `notifications` 收件箱。
3. 同批生成 `notification_dispatch_jobs`，按用户偏好决定是否创建 WebSocket / Email 等渠道任务。
4. 在线用户通过 `POST /notifications/ws-ticket` 申请短票据，并使用 `/ws/notifications?ticket=...` 建立连接；服务端推送 `NOTIFICATION_CREATED` 后等待浏览器 `ACK` 回执。
5. 若 WebSocket 推送失败或未确认，只影响渠道投递状态，不回滚站内收件箱；前端仍通过通知列表与未读数接口完成离线补偿和重同步。
6. 用户点击通知后，由前端基于 `actionCode + refType + refId` 解析真实跳转页，而不是由后端硬编码 URL。

### 3.6 内容审查时序（AI 输入/输出）
1. 用户提交 AI 请求或社区内容。
2. 后端调用统一审查引擎进行入站审查。
3. 命中 `BLOCK` 时直接返回 `MOD-1001`（输入场景）或 `MOD-1003`（社区待审场景）。
4. AI 结果返回后执行出站审查，命中高风险返回 `MOD-1002` 或做 `MASK` 脱敏。
5. 审查结果写入 `content_moderation_events`，并绑定业务 `traceId`。

### 3.7 举报处理时序
1. 用户提交举报（帖子/评论/用户）。
2. 系统执行重复举报去重与频控校验。
3. 触发阈值时自动隐藏目标内容并进入待审队列。
4. 管理员在后台执行受理/驳回/下架/恢复。
5. 处置结果写 `content_report_actions` 和 `audit_logs`，并回写举报状态。

### 3.8 导师推荐时序
1. 学生进入 `/mentors` 或切换问题场景、关键词、价格条件。
2. 后端聚合学生资料、画像标签、最近一次 AI 简历诊断和最近一次 AI 面试总结，生成学生推荐快照。
3. 后端聚合导师公开资料，生成导师推荐快照。
4. 推荐模块使用本地 `LOCAL_HASHED_BOW_V1` embedding 生成查询向量，并对候选导师做 Top-K 语义召回。
5. 召回结果继续按 frozen spec 的六维规则（问题场景、能力短板/AI 诊断问题、目标岗位/方向、质量信号、可接单、价格）重排为 100 分制。
6. 后端返回 Top 3 推荐导师，同时把本次 run 和 recall/rerank 事件写入 PostgreSQL，供后续分析与论文说明。

补充说明：
- 当前 embedding 层是“本地可替换实现”，目的在于先把召回层、快照层、日志层和数据库设计正式落地。
- 后续若接入真实 embedding provider，可复用现有快照表、向量表和 rerank 口径，不需要重做导师广场对外接口。
- 当前推荐主线正式定义为“基于内容的推荐 + 规则重排”；协同过滤不进入当前版本主链路。

### 3.9 学生画像刷新与异步规划
1. 学生资料、技能进度、社区互动或 AI 结果发生变化。
2. 后端提取画像信号，优先更新本地规则真相层，包括方向标签、优势标签、风险标签和证据计数。
3. 首次读取且快照缺失时，可保留一次同步兜底刷新，避免页面出现完全空白的画像区。
4. 对于重复触发、定时修复或后续模板总结 / LLM 润色场景，统一规划复用 `ai_async_task_jobs + ai_async_task_events` 做异步去重和后台重算。
5. 画像快照更新后，需要联动失效画像缓存，并驱动推荐快照 / 向量缓存的重刷策略。
6. 若后续启用 LLM，它只负责画像表达层的低频润色，不作为画像事实判定来源。

## 4. 可靠性设计
### 4.1 超时与重试
- 文本 AI 默认超时 15s。
- STT/TTS 默认超时 20s。
- 仅对瞬时错误重试 1 次。

### 4.2 熔断与降级
- 单供应商错误率超阈值时熔断。
- 回退顺序：同供应商备模型 -> 备供应商 -> 受控错误。
- 语音失败回退文本面试。
- 支付问题可切换模拟模式。
- 审查模块异常时可按开关降级，保障主业务可用并记录补偿审计。

### 4.3 一致性与幂等
- 支付回调幂等键：第三方交易号。
- 状态流转严格校验前置状态。
- 积分采用账本追加。
- 通知事件采用 `eventId / dedupeKey` 控制幂等；WebSocket `ACK` 只确认渠道成功，不改变业务事实。
- 通知渠道失败不回滚收件箱，依赖 `notification_dispatch_jobs` 重试调度与 `notification_dispatch_attempts` 留痕。

## 5. 安全设计
### 5.1 认证与授权
- JWT + 角色声明。
- 后端接口按角色做授权拦截。

### 5.2 数据与输入安全
- 全部公开接口 DTO 校验。
- Prompt 输入做清洗与边界限制。
- 配置中的密钥不明文回显。
- 统一敏感词匹配与风险分级策略，避免前后端规则漂移。

### 5.3 支付安全
- 回调必须验签。
- 回调异常与状态变更必须审计。

### 5.4 审计能力
- 管理员操作必须写入不可变审计记录。

### 5.5 前后端通信错误处理约定
- 前端使用 Axios 全局拦截器统一处理后端错误响应。
- 收到 `AUTH-1003`（Token 过期）时，自动尝试刷新令牌；刷新失败则跳转登录页。
- 收到 `AUTH-1004`（权限不足）时，展示无权限提示。
- 收到 `AI-xxxx` 错误时，展示用户可理解的降级消息（如“AI 服务暂时繁忙，请稍后重试”）。
- 收到 `BIZ-xxxx` 错误时，展示 `message` 字段内容。
- 收到 `MOD-xxxx` 错误时，展示通用治理提示，不回显具体敏感词。
- 所有错误响应中的 `traceId` 展示在错误提示中，便于排查。

## 6. 可观测性
- 全链路日志携带 `traceId`。
- 指标至少包括：
  - API 成功率/错误率
  - AI 延迟与错误率
  - 支付回调成功率
  - 审查命中率与误判修正率
  - 举报量、处置时效、自动隐藏触发率

## 7. 部署拓扑
- 单台 Linux 公网服务器。
- Docker Compose 双层部署：
  - `infra/docker/docker-compose.infra.prod.yml`：`postgres / redis / minio`
  - `infra/docker/docker-compose.app.prod.yml`：`caddy / web / server / interview-live`
- 对公网只暴露 `Caddy` 的 `80/443`，数据库与中间件只在宿主机本地或 Docker 私网暴露。
- 发布链采用 `GitHub Actions -> GHCR -> SSH -> 服务器自动更新应用层`；数据库导入仅在首次建站或覆盖恢复时人工执行。

## 8. 架构目标
在毕业设计周期内，提供“可靠、可演示、可回退”的工程架构。

## 9. 架构范围
覆盖前后端、AI 模块、内容治理模块、支付回调、数据层与部署路径；不包含后续微服务拆分。

## 10. 决策摘要
- 模块化单体优先于微服务。
- AI 模块集成在后端内部，不独立部署。
- 支付与 AI 统一纳入可回退机制。
- 内容治理采用统一规则引擎与后台复核，保留开关降级能力。
- 全链路 trace 与审计为强制项。

## 11. 架构验收标准
1. 核心模块按接口契约互通。
2. AI 与支付降级路径可执行。
3. 关键业务链路可追踪可审计。
