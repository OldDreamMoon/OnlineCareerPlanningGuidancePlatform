# 学生端订单创建页 UI / 需求设计规则

> 文档状态：`frozen`
> 当前定稿：2026-03-24
> 适用范围：学生端 `/consult/create`
> 用途：为后续 UI / 前端 / 后端 Agent 提供统一的正式需求基线，并作为导师广场到咨询订单链路的最终下单页设计依据。

## 0.1 当前实现对齐说明（2026-03-26）

以下补充不改变 frozen 需求，只记录当前正式实现已对齐的关键点：

- 页面已优先读取 `GET /profiles/students/me` 中的 `targetPosition`、`skillTags`、`selfIntro` 与画像标签摘要；若本地准备单草稿中已有旧值，仅作为兜底回填。
- “建议准备材料”当前已改为页内输入 + 标签管理，不再使用浏览器 `prompt` 临时补录。
- 创建订单成功后，页面会直接跳转 `/consult/orders/:orderNo` 承接后续支付、支付状态查询、补传材料与售后链路；若初始材料上传部分失败，详情页继续以显式提醒补传。

## 1. 文档目标

本文件的目标不是接口细节，也不是像素级视觉稿。

它要解决的是：

- 明确 `/consult/create` 的正式页面定位，不再停留在“导师广场临时承接页”
- 把导师广场准备单、订单创建、材料包与后续咨询会话衔接成一条完整主链路
- 为学生端订单创建页提供稳定的信息架构与功能边界
- 为后续 UI 模板设计 Agent 提供可直接执行的页面需求基线

一句话总结：

`学生端订单创建页应该被设计成“带着准备单完成正式下单确认、补全问题与材料、进入支付前最后决策”的工作台。`

## 2. 上位约束来源

以下约束来自当前项目中的上位文档与真实页面边界：

- `docs/spec/01_PRD.md`
  - 付费咨询链路已正式收口为导师广场 -> 正式订单创建页 -> 支付 -> 导师订单中心 / 履约区 -> 财务中心
- `docs/spec/07_PAYMENT_AND_ORDER_SPEC.md`
  - 咨询订单仍以 `CREATED -> PAYING -> PAID -> ANSWERED -> CLOSED / REFUNDED` 为主状态机
  - 订单需支持结构化问题输入快照与咨询材料包语义
- `docs/spec/14_FRONTEND_ROUTES_AND_PAGES.md`
  - `/consult/create` 属于学生端正式路由，而不是纯占位页
- `docs/spec/21_MENTOR_MARKETPLACE_UI_DESIGN_RULES.md`
  - 导师广场负责推荐、筛选、收藏、准备单
  - `/consult/create` 负责正式创建咨询订单，不回流承担导师发现职责
- 当前项目阶段约束
  - 宽屏桌面端为当前验收基线
  - 移动端 / 平板适配不是本轮重点

## 3. 页面定位

`/consult/create` 的正式定位不是：

- 导师广场的一个大弹窗
- 订单详情页的简化版
- 纯支付前确认页
- 即时聊天页
- 材料管理中心

它的正式定位是：

- 学生端正式订单创建页
- 导师广场准备单的承接页
- 学生在支付前完成“问题确认、材料确认、规则确认”的最后工作台

一句话：

`这个页面首先要回答“我到底要向导师下什么单、带什么材料、希望得到什么结果”，而不是“怎样尽快付款”。`

## 4. 页面职责边界

### 4.1 本页负责什么

- 展示并确认已选导师
- 承接导师广场准备单的预填内容
- 让学生填写或修改结构化咨询问题
- 让学生上传和管理初始咨询材料包
- 让学生确认咨询场景、目标与预期结果
- 展示价格、规则与风险提醒
- 创建正式咨询订单，并交给后续支付 / 订单详情链路

### 4.2 本页不负责什么

- 不负责导师发现与推荐
- 不负责导师完整详情长页
- 不负责订单支付结果页
- 不负责完整聊天履约过程
- 不负责前台文件预览中心
- 不负责显式文件版本管理页

### 4.3 与其他页面的职责拆分

- `/mentors`
  - 负责导师发现、推荐、收藏、准备单生成
- `/consult/create`
  - 负责正式下单前确认、结构化填写、材料包上传与创建订单
- `/consult/orders/:orderNo`
  - 负责订单详情、支付状态、消息、售后、评价与后续材料查看
- `/mentor/orders/:orderNo/workspace`
  - 负责导师履约视角下的消息、材料、评价与售后查看

## 5. 页面正式功能范围

本页最终正式功能固定包含以下 7 组：

1. 导师与服务确认
2. 咨询场景与咨询目标确认
3. 结构化问题填写
4. 导师广场准备单导入与编辑
5. 咨询材料包系统
6. AI 质量辅助与风险提醒
7. 创建订单并进入支付后续链路

## 6. 自动带入规则

本页必须支持从导师广场自动带入部分信息，学生进入后仍可继续编辑。

### 6.1 必带入字段

- 导师基础信息
  - `mentorUserId`
  - `displayName`
  - `avatar`
  - `companyName`
  - `jobTitle`
  - `priceFen`
  - `serviceScenes`
- 来源信息
  - `from`
  - 推荐区 / 普通列表 / 收藏列表等来源标记
- 当前咨询场景
- 准备单摘要 `summaryDraft`
- 核心问题草稿 `coreQuestions`
- 建议准备材料 `suggestedMaterials`
- 预期收获 `expectedOutcomes`
- 学生目标岗位与部分画像摘要

### 6.2 带入后的交互原则

- 导师信息默认只读
- 咨询场景可切换，但切换后应提示是否刷新准备单草稿
- 准备单文字、核心问题、预期收获都允许继续编辑
- 建议准备材料不会自动等同于“已上传材料”，仍需学生实际确认和上传

## 7. 页面信息架构

正式页面采用宽屏桌面端双栏结构：

1. 页面头部
2. 左侧主工作区
3. 右侧订单摘要侧栏

### 7.1 页面头部

页面头部必须包含：

- 页面标题：`创建咨询订单`
- 副标题：强调“整理问题、确认材料、正式下单”
- 返回导师广场入口
- 当前来源提示

### 7.2 左侧主工作区

左侧主工作区固定包含：

1. 导师确认卡
2. 咨询场景与咨询目标区
3. 结构化问题区
4. 准备单导入与编辑区
5. 咨询材料包区
6. AI 检查与风险提醒区
7. 提交操作区

### 7.3 右侧订单摘要侧栏

右侧侧栏固定包含：

- 导师简要卡片
- 当前场景
- 当前问题摘要
- 材料包数量摘要
- 预期结果标签
- 价格摘要
- 服务规则摘要
- 主按钮：`创建订单并继续`

## 8. 导师确认卡

导师确认卡必须展示：

- 导师头像
- 导师姓名
- 公司与职位
- 擅长方向标签
- 服务场景标签
- 当前价格
- 当前可接单状态

本区操作：

- `返回导师广场重新选择`
- 不在本页提供复杂导师对比

## 9. 咨询场景与咨询目标区

### 9.1 咨询场景

必须展示当前场景，并支持以下规则：

- 默认继承导师广场选择结果
- 可切换场景
- 切换场景后应提示：是否保留当前草稿，或重新生成准备单

### 9.2 咨询目标

本区用于把“我要问什么”变成“我希望这次服务达成什么”。

建议至少支持以下目标项：

- 获得简历修改建议
- 获得项目表达优化建议
- 获得岗位方向建议
- 获得模拟面试复盘建议
- 获得 Offer 决策建议
- 获得下一步行动清单

允许多选。

## 10. 结构化问题区

这是本页核心区，不应只保留一个大文本框。

### 10.1 正式输入结构

本页正式要求至少包含以下字段：

- `本次最想解决的问题`
- `我的背景情况`
- `我已经尝试过什么`
- `我希望导师给出的帮助`
- `额外补充说明`

### 10.2 规则

- 每一项都允许为空，但页面应给出完整度提示
- 系统最终仍会组合成一段 `questionText` 作为订单主问题文本
- 前端应保留结构化字段，便于后续回填和编辑

### 10.3 设计原则

- 结构化输入要明显优于“只扔一个大文本框”
- 帮学生降低表达门槛
- 帮导师更快理解上下文
- 帮平台沉淀更稳定的订单快照

## 11. 准备单导入与编辑区

### 11.1 本区定位

本区用于承接导师广场的 AI 准备单，不是单独再做一次新推荐。

### 11.2 正式内容

必须支持查看和编辑：

- 当前困扰摘要
- 三个核心咨询问题
- 建议准备材料
- 预期收获

### 11.3 交互规则

- 支持 `重新生成`
- 支持 `清空重写`
- 支持手动修改全部文本
- 支持将某条核心问题直接带入结构化问题区

## 12. 咨询材料包系统

材料包系统是本页正式能力，不是附属小功能。

### 12.1 功能定位

材料包用于：

- 帮学生把咨询上下文真正带给导师
- 降低“下单后还要来回解释”的成本
- 让导师履约时能看到完整的当前有效材料
- 让聊天中的补充材料有稳定归档位置

### 12.2 正式能力范围

本页材料包系统必须支持：

- 多文件上传
- 材料类型选择
- 材料说明填写
- 已上传材料列表
- 删除当前材料
- 在聊天过程中继续补充或替换材料

本页材料包系统当前明确不要求：

- 文件预览
- 在线批注
- 前台版本管理页
- 文件夹体系

### 12.3 正式材料类型

建议固定类型至少包括：

- `简历`
- `岗位 JD`
- `项目材料`
- `Offer 材料`
- `补充材料`

### 12.4 单槽位与多槽位规则

本页必须采用“单槽位材料 + 多槽位材料混合”方案：

- 单槽位材料
  - `简历`
  - `岗位 JD`
  - 同一时刻默认只保留最新有效副本
- 多槽位材料
  - `项目材料`
  - `Offer 材料`
  - `补充材料`
  - 可并存多份当前有效文件

### 12.5 创单页材料区固定内容

材料区必须包含：

- 材料区标题
- 场景化提示文案
- 建议材料清单
- 上传入口
- 已上传材料列表
- 每个材料的类型、文件名、大小、说明
- 缺失材料提醒

### 12.6 材料区交互规则

- 上传后立即在当前材料列表中可见
- 学生可删除当前材料
- 若上传单槽位材料新文件，应提示“将替换当前最新版”
- 多槽位材料默认是追加，不自动覆盖

## 13. 聊天阶段的材料更新规则

本页的材料包设计必须考虑后续咨询消息页的持续使用。

### 13.1 正式规则

- 学生在聊天过程中可继续上传补充材料
- 学生在聊天过程中可替换简历或岗位 JD 等单槽位材料
- 替换后，导师前台默认只看到最新有效副本
- 旧文件不在导师前台主视图中继续展示

### 13.2 系统内部留痕原则

虽然前台不做显式版本管理页，但系统内部仍应保留：

- 被替换文件记录
- 替换关系
- 上传时间
- 上传来源

也就是说：

- 前台体验：只看当前有效材料
- 系统内部：保留 `SUPERSEDED` 留痕，用于审计、售后和问题追溯

### 13.3 消息流联动

聊天阶段若发生材料更新，消息流建议插入系统事件：

- `学生已更新简历`
- `学生已更新岗位 JD`
- `学生已补充项目材料`

消息流的作用是“提醒发生过更新”，不是承载完整版本历史。

## 14. AI 质量辅助与风险提醒

本页建议正式纳入轻量 AI / 智能辅助，而不是只做纯表单。

### 14.1 推荐纳入的能力

- 问题完整度检查
- 材料缺失提醒
- 敏感信息脱敏提醒

### 14.2 问题完整度检查

目标：

- 判断学生是否把问题写清楚
- 判断是否缺背景、缺目标、缺预期结果

输出形式建议：

- `信息较完整`
- `建议补充背景情况`
- `建议补充期望导师输出`

### 14.3 材料缺失提醒

根据当前咨询场景提示材料是否不足。

示例：

- 简历诊断：未上传简历时提示
- 项目表达：未上传项目材料时提示
- Offer 决策：未上传 Offer 材料时提示

### 14.4 敏感信息提醒

如果学生输入中出现以下高敏信息，应提示：

- 手机号
- 邮箱
- 身份证号
- 住址
- 其他不必要个人隐私信息

## 15. 服务规则确认区

本区必须明确告诉学生：

- 当前服务形式
- 回复时效
- 是否允许聊天阶段补充材料
- 售后 / 退款规则摘要
- 隐私与脱敏提醒

本区作用是：

- 防止学生“带着错误预期下单”
- 让页面更像正式交易确认页，而不是普通问答表单

## 16. 右侧订单摘要侧栏

右侧侧栏必须是固定摘要区，而不是装饰区。

建议固定展示：

- 导师头像 / 姓名 / 公司职位
- 当前咨询场景
- 当前问题摘要
- 已选目标
- 当前材料数量
- 当前价格
- 服务规则摘要
- 主按钮

### 16.1 主按钮文案

建议使用：

- `创建订单并继续`

不建议直接写成：

- `立即支付`

因为正式语义仍是先创建订单，再进入支付 / 订单详情后续链路。

## 17. 页面主链路

本页正式主链路固定为：

1. 学生从导师广场带着准备单进入 `/consult/create`
2. 页面读取导师、场景、准备单与学生上下文
3. 学生确认导师和咨询场景
4. 学生编辑结构化问题与准备单内容
5. 学生上传或确认初始材料包
6. 系统执行轻量完整度 / 风险提醒
7. 学生确认价格与规则
8. 学生创建咨询订单
9. 页面进入支付或订单详情后续链路

当前实现补充：

- 创建成功后默认立即进入订单详情页，而不是停留在本页展示成功卡片。

## 18. 明确不纳入范围的功能

以下能力当前明确不做：

- 文件在线预览
- 文件版本历史时间轴
- 多导师同时对比下单
- 优惠券 / 满减 / 积分抵扣系统
- 即时聊天预沟通再下单
- 多步强引导 wizard
- 复杂文件夹管理

## 19. 依赖的 API / DB 契约方向

本文件不是 API 文档，但为实现正式功能，以下契约被视为正式依赖：

- `POST /consult/orders`
  - 支持结构化问题快照、场景与准备单快照
- `GET /consult/orders/{orderNo}`
  - 支持返回结构化订单快照与材料摘要
- `GET /consult/orders/{orderNo}/attachments`
  - 支持读取当前有效材料包
- `POST /consult/orders/{orderNo}/attachments/batch`
  - 支持多文件上传与替换策略
- `DELETE /consult/orders/{orderNo}/attachments/{attachmentId}`
  - 支持删除当前材料

数据库方向至少需要：

- `consult_orders`
  - 增加场景、结构化问题与准备单快照字段
- `consult_order_attachments`
  - 保存订单材料包与被替换文件的生命周期留痕

## 20. 验收标准

本页正式验收标准如下：

1. 学生从导师广场进入后，能看到导师、场景与准备单的稳定预填结果。
2. 页面不是单一大文本框，而是结构化问题工作区。
3. 页面支持多文件材料包上传，并区分材料类型。
4. 简历 / 岗位 JD 等单槽位材料默认只保留最新有效副本。
5. 项目材料 / Offer 材料 / 补充材料支持多份并存。
6. 当前阶段前台不要求文件预览，也不要求显式版本管理页。
7. 聊天阶段补充或替换材料后，导师默认只看到当前有效材料。
8. 页面能展示价格、规则、风险提醒与明确主操作。
9. 宽屏桌面端结构稳定、层级清晰，适合作为答辩演示页与后续模板设计输入。
