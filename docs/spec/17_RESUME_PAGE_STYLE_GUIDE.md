# AI 简历优化页样式设计规则

> 文档状态：`evolving`
> 适用范围：学生端 `/ai/resume`
> 用途：为后续 AI / 设计 Agent 提供统一的 UI 设计边界、视觉方向与页面规则，避免只做“模板换皮”或偏离当前真实产品能力。

## 1. 文档目标

本文件不是接口规范，也不是像素稿，而是一份“可直接交给其他 AI 继续出稿”的样式设计规则文档。

它解决三个问题：

1. 明确 `/ai/resume` 当前真实能力边界，避免 UI 设计超前到假功能。
2. 对齐学生端现有设计语言，避免简历页做成孤立的外来模板页。
3. 给出足够具体的布局、视觉、文案、路由拆分与状态规则，让后续 AI 输出更稳定。

## 2. 上位约束来源

以下约束来自现有产品与前端文档：

- `docs/spec/01_PRD.md`
  - P0 主能力之一是“AI 简历优化（文本输入输出）”。
  - 学生核心旅程之一是“选择目标岗位 -> 提交简历 -> 获得结构化建议”。
- `docs/spec/14_FRONTEND_ROUTES_AND_PAGES.md`
  - `/ai/resume` 是学生端稳定开放主路由之一。
  - 当前学生端人工审查与修正以宽屏桌面端为验收基线。
- `docs/spec/15_FRONTEND_REFACTOR_CHECKLIST.md`
  - 简历页仍需继续收口：上传区/结果区布局、结构化结果、双模式区分、失败态。
- `docs/spec/06_AI_MODULE_SPEC.md`
  - 文本简历优化支持 SSE 分段输出。
  - PDF 简历优化已接通真实模型能力。
  - 结果会落历史并支持精确绑定导出 PDF。

## 3. 当前真实能力边界

后续任何 UI 方案都必须以“真实能力”而不是“理想能力”为准。

### 3.1 已有能力

- 学生角色可访问 `/ai/resume`。
- 支持两种输入模式：
  - 文本模式：粘贴简历文本。
  - PDF 模式：上传 PDF 文件。
- 支持填写目标岗位。
- 文本模式支持 SSE 分段展示：
  - 摘要
  - 亮点
  - 风险
  - 建议
- 结果会写入历史记录。
- 当前结果可绑定 `recordId` 并导出 PDF。
- 可查看历史详情、复制结果、删除历史。
- 可从页面跳转到导师页继续沟通。

### 3.2 不应假装已经完成的能力

- 不要把页面设计成“自动同步给导师”。
- 不要设计“导师实时协作批注”。
- 不要设计“在线逐页 PDF 标注编辑器”。
- 不要设计“AI 自动代写整份简历并一键覆盖原文”的主流程。
- 不要把调试态元信息放成主视觉核心内容。
- 不要把不存在的打分体系包装成正式 SSOT。
  - 模板中出现过“ATS 竞争力评分”，当前真实产品没有稳定、可信的统一评分体系，不能做成页面主 KPI。

### 3.3 本轮已确认纳入下一阶段 UX 设计范围的能力

以下能力已经由当前会话确认，可以作为下一版 UI 重点设计对象：

- 岗位 JD 对照工作台
- Before / After 改写沙盘
- 本地草稿自动保存
  - 仅保留当前草稿自动恢复能力
  - 当前不做多快照、多版本时间线
- 简历结构完整度地图
  - 允许为每个小项附带简单评分
  - 该评分仅用于前端自检与可视化，不包装成权威 ATS 分
- 目标语境切换
- 长页阅读辅助

说明：

- 上述能力属于“下一阶段前端体验设计目标”，不代表后端能力已全部就绪。
- 后续 UI 出稿时，可以大胆围绕这些功能设计，但必须继续遵守本文件中的真实性边界。

## 4. 页面定位

`/ai/resume` 的定位不是“炫技 AI 页面”，而是学生工作台体系下的一组高价值求职工具页。

应满足以下定位：

- 它属于“学生求职准备工作区”。
- 它的任务是帮助学生快速看清简历问题，而不是替代整个简历编辑器。
- 它必须让“提交材料 -> 获得分析状态 -> 进入结果复盘中心 -> 回看历史 -> 导出继续使用”这条路径尽可能顺滑。
- 它应该比普通表单页更有产品感，但不能脱离学生端整体视觉体系。
- 它不应继续把“输入、完整结果、历史、历史详情、所有增强工具”全部硬塞在一个首屏里。

## 5. 整体设计方向

### 5.1 视觉关键词

- 明亮
- 冷静
- 清晰
- 专业
- 轻科技
- 高信息密度但不压迫

### 5.2 避免的方向

- 纯黑深色科幻座舱
- 过度霓虹感
- 赛博终端风
- 过多渐变叠加导致阅读吃力
- 看起来像管理员后台
- 看起来像完全独立于学生端体系的营销页

### 5.3 推荐基线

简历页应延续学生端现有基线：

- 背景使用浅色大面积渐变和柔和光斑
- 顶栏使用半透明白色玻璃感
- 主卡片使用白色或近白色卡面
- 强调色以 `indigo / violet / teal / emerald` 为主
- 圆角偏大，但不要卡通化
- 阴影柔和，不做厚重投影堆叠

## 6. 与学生端统一的强规则

以下规则是硬约束，不建议后续 AI 随意突破。

### 6.1 页面壳层

- 顶栏风格应与学生工作台、资料中心保持同一体系：
  - 半透明白底
  - 大圆角图标方块
  - 亮色背景
  - `max-w-[96rem]` 宽容器
- 主容器宽度按学生端现有桌面规则处理，不回退成较窄的营销页宽度。
- 页面应保持“工作区”属性，而不是单纯的 landing section 拼接。

### 6.2 桌面端优先

- 当前阶段只需优先把宽屏桌面端做对。
- 可以保留移动端基本可用，但不把移动端作为本轮设计主约束。
- 布局可以大胆使用宽屏横向结构，但必须保证阅读顺序清晰。

### 6.3 信息诚实

- UI 中不能把接口路径、SSE、provider、model 等技术信息作为主卖点。
- 这些信息如果保留，只能下沉到“辅助信息 / 元信息 / 调试信息”层级。
- 主界面重点永远是学生能看懂的求职语义。

## 7. 页面与路由信息架构

当前已确认：AI 简历功能至少拆成两个页面路由，不再继续追求“单页塞满全部能力”。

### 7.1 推荐路由拆分

推荐最小双路由结构：

1. `提交操作页`
   - 推荐路径：
     - `/ai/resume`
     或
     - `/ai/resume/compose`
2. `结果复盘中心`
   - 推荐路径：
     - `/ai/resume/review`
     或
     - `/ai/resume/results/:recordId`

说明：

- 若团队希望先少改路由，可保留 `/ai/resume` 作为操作页主入口。
- 结果复盘中心应能查看“本次详细结果 + 历史记录 + 历史详情”，因此命名上更适合 `review / results / replay-center` 这一类语义。
- 当前更推荐 `review` 语义，因为它比单纯 `result` 更能覆盖“当前结果 + 历史复盘”。

### 7.2 路由 A：提交操作页

职责：

- 选择目标语境
- 填写目标岗位
- 粘贴 JD 或岗位要求
- 选择输入模式
- 上传 PDF 或输入文本
- 自动保存当前草稿
- 发起分析
- 在本页以完成弹窗、错误提示和轻量入口反馈基础状态

该页只应展示“轻量结果状态”，不承载完整结果阅读。

轻量结果状态可包括：

- 已提交分析
- 正在分析中
- 已完成，可进入复盘中心
- 失败，可返回修改后重试

### 7.3 路由 B：结果复盘中心

职责：

- 查看本次完整结果
- 查看结构化结果
- 使用长页阅读辅助
- 进入 Before / After 改写沙盘
- 查看结构完整度地图
- 查看历史记录
- 查看历史详情
- 导出 PDF

该页是“结果阅读与继续打磨”的主战场。

### 7.4 提交操作页的信息架构

建议分为四层：

1. 页面抬头 / 任务定位
2. 基础信息区
   - 目标语境切换
   - 目标岗位
3. 输入工作区
   - JD 对照工作台
   - PDF / 文本模式
   - 草稿自动保存状态
   - 草稿恢复确认弹窗
4. 底部提交操作行
   - 开始分析
   - 清空重填
   - 轻量错误提示 / 最近复盘入口

### 7.5 结果复盘中心的信息架构

建议分为五层：

1. 顶部结果概览
2. 总评摘要
3. 结构化诊断结果
4. 改写与继续打磨工具
5. 历史记录与历史详情

### 7.6 信息主次规则

- “提交操作页”的主角是输入与准备动作。
- “结果复盘中心”的主角是结果阅读与继续打磨。
- 历史区只能存在于复盘中心，不应在提交页中占据核心位置。
- 如果必须在提交页出现历史入口，也只保留轻量入口，不直接展开完整历史工作区。

## 8. 布局规则

### 8.1 总体布局建议

双路由结构下，应分别设计两套桌面端布局。

### 8.2 提交操作页布局建议

推荐桌面端结构：

1. 顶部壳层导航
2. 首屏概览区
3. 主工作区：
   - 左侧或上方：目标语境 / 目标岗位 / JD 对照
   - 右侧或下方：PDF / 文本输入区
4. 底部操作行与轻量反馈

说明：

- 提交页可以更偏“整洁、有秩序的工作台”。
- 不要在提交页下方继续展开完整结果卡和完整历史区。
- 首屏状态信息不应继续使用很小的 outline badge，更推荐做成更醒目的大号胶囊卡 / 信息卡。

### 8.3 结果复盘中心布局建议

推荐桌面端结构：

1. 顶部壳层导航
2. 结果概览区
3. 主阅读区：
   - 总评
   - 结构化结果
   - 改写沙盘
4. 次级历史区 / 历史详情区
5. 长页阅读辅助区

### 8.4 比例建议

- 首屏概览区可以使用 `1.3 ~ 1.7 : 0.7 ~ 1` 的双栏比例
- 提交页主工作区可以使用：
  - 信息区 `5`
  - 输入区 `7`
  或
  - 信息区 `4`
  - 输入区 `8`
- 复盘中心主工作区可以使用：
  - 主结果区 `7 ~ 8`
  - 侧边辅助区 `4 ~ 5`
- 历史区不建议比主结果区更宽、更强、更重
- 改写沙盘可以作为结果区内部的独立大卡，不建议挤成窄侧栏

### 8.5 宽度与留白

- 页面内容容器统一使用学生端宽容器思路
- 卡片之间允许较大留白，但单张卡内部不要过空
- 视觉目标不是“松散”，而是“清晰且稳”

## 9. 视觉语言规则

### 9.1 色彩

推荐色彩关系：

- 页面背景：浅蓝白渐变 / 冷白渐变
- 主强调色：indigo
- 次强调色：teal / emerald
- 风险色：amber
- 错误色：rose

规则：

- 一个页面最多 1 个主强调色 + 1 到 2 个辅助强调色
- 渐变要服务于层次，不要每张卡都渐变
- 强调色主要用于：
  - 主按钮
  - hero 卡
  - 关键标签
  - 激活态

### 9.2 圆角

- 外层大卡：`2rem` 到 `2.35rem`
- 中层卡：`1.25rem` 到 `1.6rem`
- 小型胶囊：圆角全满

### 9.3 阴影

- 阴影应该柔和、扩散、空气感强
- 避免又黑又硬的后台风阴影
- 不要在每层都叠很重的阴影

### 9.4 边框

- 建议使用低对比浅边框辅助分层
- 边框存在感应弱于卡片体块
- 风险态和错误态才允许更明确的边框色

## 10. 文案与语气规则

### 10.1 页面文案语气

应该像：

- 求职辅助工具
- 清晰、诚实、专业
- 鼓励式，但不浮夸

不应该像：

- 技术调试面板
- 后台日志系统
- 大模型炫技宣传页

### 10.2 文案用词

推荐：

- 简历材料
- 目标岗位
- 本次总评
- 亮点
- 风险
- 建议
- 历史记录
- 导出报告
- 继续打磨

避免：

- Provider
- Model
- SSE
- Stream
- Workspace
- Debug
- ATS 评分

说明：

- 如果某些技术词必须出现，放在低层级元信息区，不进入首屏主文案。

## 11. 组件级规则

### 11.1 顶栏

- 必须与学生端统一
- 建议包含：
  - 品牌图标
  - 页面标题
  - 学生端相关导航入口
  - 返回工作台
  - 导师页快捷入口
- 不要把顶栏做成单纯的 logo + 按钮孤岛

### 11.2 模式切换器

- 文本 / PDF 必须是同级切换
- 切换态要明显
- 不建议设计成过度复杂的 segmented tabs
- 切换后输入区域要明确变化，不只是标签变化

### 11.2.1 目标语境切换器

本轮确认应新增“目标语境切换”。

职责：

- 告诉系统或页面，当前简历准备属于什么语境
- 帮助用户理解建议会偏向哪类求职目标

推荐语境：

- 实习投递
- 校招正式批
- 社招初阶
- 技术岗
- 非技术岗

规则：

- 语境切换器应位于提交操作页的前部，不应埋太深
- 语境切换应影响页面提示文案、结构完整度提示与改写建议的展示语气
- 不必做成复杂树状筛选，优先单层可快速切换

### 11.2.2 岗位 JD 对照工作台

本轮确认应新增“岗位 JD 对照工作台”。

职责：

- 让用户粘贴岗位描述、招聘要求或 JD 摘要
- 建立“岗位要求 vs 当前简历”的对照语境

推荐结构：

- 主体：岗位要求 / JD 输入区
- 辅助：一条轻量说明条，提示用户这里会作为岗位对照语境使用

规则：

- JD 区块是提交操作页的核心差异化能力之一，不能被隐藏成低优先级抽屉
- 但它也不能压过“简历输入本身”，应与简历材料区形成并列关系
- 不建议在该区块里引入复杂的职位抓取、自动 URL 解析等假能力
- 当前不再展示单独的“关键词提炼预览卡”或 `JD Workspace` 文案

### 11.3 上传区

- 必须看起来像“文档处理区”，而不是普通文件 input
- 应包含：
  - 上传动作
  - 当前文件名
  - 文件状态
  - 移除动作
- 当文件已选择时，文件信息应优先直接嵌入上传框内部，而不是再拆成上传框下方的独立状态卡
- 不建议假装支持图片、Word、多文件上传，如果当前并不支持

### 11.4 结果卡

- 本次结果首卡必须突出“总评摘要”
- 亮点、风险、建议三类卡可以共用统一组件语言
- 三类卡应保持：
  - 同结构
  - 不同强调色
  - 清晰的视觉分区

### 11.4.1 简历结构完整度地图

本轮确认应新增“简历结构完整度地图”。

职责：

- 帮助用户快速看清简历哪些模块完整、哪些模块薄弱

推荐模块：

- 基本信息
- 教育背景
- 项目经历
- 实习经历
- 技能描述
- 自我介绍
- 量化成果
- 岗位匹配度表达

评分规则：

- 允许每一项附带简单评分
- 推荐使用 `1-5` 或 `0-5` 的轻量评分
- 评分只用于前端可视化与自检，不包装成官方 ATS 分数

展示建议：

- 可使用网格卡、条形进度、矩阵地图、小型雷达替代方案
- 不建议使用占满首屏的大雷达图

### 11.4.2 Before / After 改写沙盘

本轮确认应新增“Before / After 改写沙盘”。

职责：

- 把抽象建议转成可执行改写
- 让用户直接看到“原写法 / 推荐写法 / 我的改写”

推荐结构：

- 原句
- AI 推荐改写
- 我的编辑区
- 采纳 / 复制 / 继续改写操作

规则：

- 改写沙盘应位于结果复盘中心，而不是提交操作页
- 它属于“继续打磨工具”，不是首屏主视觉
- 不建议一次展示过多条改写任务，避免造成压迫感

### 11.4.3 长页阅读辅助

本轮确认应新增“长页阅读辅助”。

职责：

- 在结果内容变长后，帮助用户不迷路

推荐能力：

- 吸顶锚点导航
- 当前阅读进度提示
- 一键返回顶部
- 当前章节高亮
- 支持折叠部分长内容

规则：

- 长页辅助只存在于结果复盘中心
- 它应弱于正文，不喧宾夺主
- 不要做成一直闪动或遮挡正文的大型悬浮组件

### 11.5 历史列表

- 每条历史记录至少展示：
  - 时间
  - 摘要
  - 是否消耗积分
- 不要只展示 ID
- 不要让列表项过高，否则历史区会显得太笨重

### 11.6 历史详情

- 历史详情的结构应与本次结果保持同一阅读逻辑
- 导出、复制、删除按钮要有明确优先级
- 删除应显著弱于导出

### 11.7 本地草稿自动保存

本轮确认应新增“本地草稿自动保存”。

职责：

- 自动保留用户未提交完的内容
- 在返回页面时恢复编辑上下文

建议保存内容：

- 目标语境
- 目标岗位
- JD 输入内容
- 文本简历内容
- 已选择但尚未重新上传的文件名提示状态
  - 说明：真实文件对象通常无法完整持久化恢复，前端只需诚实展示“你上次选择过文件，请重新上传”

规则：

- 只做当前草稿恢复，不做多快照时间线
- 必须提供“清空当前草稿”能力
- 自动保存提示应轻量，不要频繁打断
- 若检测到已恢复草稿，推荐在页面加载后以轻量确认弹窗提示，而不是把说明栏长期占在正文首屏

## 12. 状态设计规则

页面必须覆盖以下状态，而且每个状态都要可被一眼理解。

### 12.1 空态

- 告诉用户先做什么
- 提醒支持哪些输入方式
- 不要只有一个空白占位框

### 12.2 分析中

- 文本模式：
  - 强调“分段生成中”
  - 已返回的内容要即时可见
- PDF 模式：
  - 强调“正在解析整份简历”
  - 不要伪装出实际上不存在的逐页扫描能力

### 12.2.1 提交操作页的轻量反馈

由于已确认采用双路由结构，提交操作页应额外覆盖：

- 未提交
- 提交中
- 分析已开始
- 分析完成，可进入复盘中心
- 分析失败，可回到编辑状态

规则：

- 提交页不再单独做整块“状态反馈大卡”
- 完成态优先通过轻量弹窗给出结果概览与“进入复盘中心”主按钮
- 失败态以内联错误提示出现即可，不要把错误展开成一整块结果区
- 若用户停留在提交页，可保留“查看最近复盘”的轻量入口，但不继续在本页展开完整报告

### 12.3 成功态

- 先展示总评
- 再展示结构化结果
- 再展示下一步行动

### 12.4 错误态

必须能区分至少三类问题：

- 文件格式不支持
- 接口 / 网络失败
- 内容治理拦截

错误态设计原则：

- 明确说明问题
- 给出下一步动作
- 不要只弹红字

### 12.5 无历史态

- 告诉用户历史会自动保存
- 引导先完成第一轮分析
- 不要使用过重的空态插画

### 12.6 草稿恢复态

- 页面重新打开时，如果存在本地草稿，应在进入页时给出一层轻量确认弹窗
- 弹窗应清楚说明恢复了什么内容，以及哪些文件状态需要重新上传
- 应允许用户：
  - 继续使用草稿
  - 清空草稿重新开始

## 13. 动效规则

### 13.1 允许的动效

- 卡片淡入上浮
- 分段结果依次出现
- 轻量光斑漂浮
- loading 旋转或脉冲
- 结果 reveal 动画

### 13.2 不建议的动效

- 大面积扫描线来回扫全屏
- 高频闪烁
- 过强的霓虹辉光
- 页面滚动时复杂视差
- 过重 3D 翻转

### 13.3 动效原则

- 动效服务于“状态变化”和“阅读顺序”
- 不要为了“AI 感”而增加噪音

## 14. 设计禁区

后续 AI 出稿时，以下方案默认视为偏离：

- 整页改成深色赛博风
- 顶栏脱离学生工作台体系重新设计
- 页面宽度收窄回营销页规格
- 在提交页中直接展开完整历史区与完整复盘中心
- 把历史区做得比本次结果更抢眼
- 用“综合评分 / ATS 分数”作为主设计锚点
- 用大量英文术语替代求职语义
- 把“简单评分”设计成高风险、权威化、极强判断性的正式结论
- 做多快照时间线、版本宇宙、复杂 diff 中心，导致当前阶段范围膨胀
- 引入当前不存在的导师协同、在线批注、自动同步、多人协作等假功能

## 15. 推荐的页面设计句式

给其他 AI 做页面时，建议围绕以下语义组织：

- 这份简历当前最突出的问题是什么
- 哪些经历是亮点
- 哪些地方会影响岗位匹配度
- 下一步先改哪里最有效
- 这轮结果如何被保存、回看和导出

## 16. 可直接给其他 AI 的摘要提示词

下面这段可以直接复制给其他 AI，用于继续做视觉探索：

```text
请为学生端 `/ai/resume` 设计桌面端 UI。页面属于“AI Career 学生工作台”体系，不是独立 landing，也不是管理员后台。

真实能力边界：
- 学生可用
- 支持 PDF 上传和文本粘贴两种模式
- 支持填写目标岗位
- 文本模式支持分段返回摘要/亮点/风险/建议
- 结果会写入历史，支持查看历史详情、导出 PDF、删除历史
- 不支持自动同步导师、不支持在线协同批注、不存在可信统一 ATS 评分体系

本轮已确认纳入下一阶段设计范围：
- 岗位 JD 对照工作台
- Before / After 改写沙盘
- 本地草稿自动保存（不做多快照）
- 简历结构完整度地图（允许每小项简单评分）
- 目标语境切换
- 长页阅读辅助

路由结构要求：
- 至少拆成两个页面路由
- 页面 A：提交操作页，负责填写信息、上传材料，并以轻量弹窗 / 内联提示反馈基础状态
- 页面 B：结果复盘中心，负责完整结果阅读、改写沙盘、历史记录与历史详情
- 不要再做成单页塞满输入、完整结果、历史和全部增强功能的结构

设计目标：
- 明亮、冷静、专业、轻科技
- 桌面端宽屏优先
- 与学生工作台和资料中心统一视觉语言
- 主容器宽度按 `max-w-[96rem]` 级别考虑
- 页面结构清晰区分：提交操作页与结果复盘中心
- 提交页聚焦“准备与提交”，复盘中心聚焦“阅读与继续打磨”

强约束：
- 顶栏必须延续学生端亮色玻璃感工作区风格
- 不要做成深色赛博风
- 不再暴露输出语言选择
- JD 对照区不再展示关键词提炼预览卡
- 提交页不再单独设计大块状态反馈卡
- 不要暴露太多接口/模型/调试术语
- 结果复盘中心必须突出“总评摘要、亮点、风险、建议”
- 历史区是辅助区，不能压过本次结果
- 简单评分只能作为自检提示，不能包装成权威 ATS 分
- 提交页不得展开完整历史工作区

请输出：
1. 页面整体概念说明
2. 双路由桌面端信息架构
3. 提交操作页关键区块草图描述
4. 结果复盘中心关键区块草图描述
5. 色彩/圆角/阴影/动效建议
6. 为什么它比当前模板式页面更适合毕业设计答辩展示
```
