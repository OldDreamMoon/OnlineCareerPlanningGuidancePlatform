# 通知中心 UI 设计规则（中文）

> **文档状态**：`evolving` · 最后审核：2026-03-28
>
> **适用范围**：学生 / 导师 / 企业共享路由 `/notifications`
>
> **用途**：定义通知中心正式产品化 UI 的页面定位、信息架构、核心功能与交互基线。本文件不以当前生成式前端原型为依据，而以平台用户的真实使用需求为优先判断。
>
> **关联文档**：
> - [`14_FRONTEND_ROUTES_AND_PAGES.md`](docs/spec/14_FRONTEND_ROUTES_AND_PAGES.md)
> - [`26_PLATFORM_NOTIFICATION_SYSTEM_SPEC.md`](docs/spec/26_PLATFORM_NOTIFICATION_SYSTEM_SPEC.md)

## 1. 文档目标

本文件不是接口清单，也不是单纯的视觉灵感备注。

它的目标是：

- 明确 `/notifications` 在正式产品中的正确定位
- 定义通知中心在宽屏桌面端下应该提供的主要功能、元素和信息层级
- 避免后续前端实现继续停留在“联调页 / 调试页 / 技术状态页”的层级
- 为后续页面重构、模板设计和多角色统一体验提供清晰基线

一句话总结：

`通知中心应该是用户统一查看消息、判断优先级并继续回到业务主链路的动作工作台，而不是一张简单的通知流水表。`

## 2. 页面定位

### 2.1 正确定位

`/notifications` 的正式定位是：

- 平台统一通知中心
- 学生 / 导师 / 企业共享的消息收件箱
- 实时提醒、离线补偿与动作回流的统一承接页
- 用户判断“哪些消息值得我现在处理”的优先级工作台

### 2.2 错误定位

`/notifications` 不应该被做成：

- 技术联调用的状态监控页
- 只会显示时间和文案的基础列表页
- 某个单一业务模块的附属子页
- 管理员式消息后台
- 聊天中心或客服会话页

### 2.3 页面首先要回答的问题

用户进入通知中心后，首屏应该立刻回答以下问题：

1. 我现在有多少条值得关注的消息？
2. 哪些通知需要我继续处理？
3. 这些通知分别来自哪个业务模块？
4. 我能否直接从这里继续回到对应页面？
5. 当前实时提醒和桌面提醒是否正常工作？

## 3. 用户核心需求

### 3.1 学生

学生最关注的是：

- AI 简历 / AI 面试结果是否已经出来
- 咨询订单是否有导师回复、支付变化或售后结果
- 悬赏任务是否有审核结果或继续接触
- 社区事务通知是否值得回看
- 离开页面后错过的结果是否能补看

### 3.2 导师

导师最关注的是：

- 新订单、学生回复、履约变化、售后状态
- 认证状态变化
- 是否存在需要尽快处理的高优先级提醒

### 3.3 企业

企业最关注的是：

- 学生提交成果后的审核提醒
- 继续接触 / 未入选等动作结果的留痕回看
- 企业认证与系统公告

### 3.4 共性需求

三个角色共享的核心诉求是：

- 不错过重要事务
- 不被噪音信息淹没
- 能从通知直接回到正确业务页
- 能知道提醒是否真的开启

## 4. 上位约束与首版边界

### 4.1 上位约束

- [`26_PLATFORM_NOTIFICATION_SYSTEM_SPEC.md`](docs/spec/26_PLATFORM_NOTIFICATION_SYSTEM_SPEC.md)
  - 已定义通知中心是统一收件箱真相层
  - 已定义 WebSocket、浏览器提醒、偏好设置与跳转动作语义
- [`14_FRONTEND_ROUTES_AND_PAGES.md`](docs/spec/14_FRONTEND_ROUTES_AND_PAGES.md)
  - 已声明 `/notifications` 为学生 / 导师 / 企业复用的正式路由
- 当前毕业设计前端审查阶段以宽屏桌面端为主验收基线

### 4.2 首版必须围绕当前真实能力设计

首版通知中心 UI 必须围绕当前已存在能力设计：

- 站内收件箱列表
- 未读数同步
- 单条已读 / 全部已读
- WebSocket 实时同步
- 浏览器桌面提醒授权
- 分类通知偏好
- 结构化动作跳转与兜底降级

### 4.3 首版不强制纳入

下列能力可以预留，但不应作为当前正式 UI 的阻塞前提：

- 服务端关键词搜索
- 通知归档
- 恢复未读
- 批量多选管理
- 复杂安静时段编辑器
- 消息置顶 / 收藏
- 营销消息频道管理

## 5. 设计原则

### 5.1 动作优先，而不是信息堆叠

通知中心的核心目标不是“把所有通知都展示出来”，而是帮助用户更快进入下一步动作。

因此页面必须优先强化：

- 待处理
- 重要程度
- 下一步入口

而不是优先强化：

- 技术字段
- 原始 payload
- 系统链路术语

### 5.2 收件箱是真相层，实时只是加速层

UI 必须明确传达：

- 通知会稳定留存在收件箱
- 实时提醒只是更快，不是唯一来源
- 即使错过弹窗，也能回到通知中心补看

### 5.3 共享骨架，角色回跳差异化

通知中心的主体工作区应尽量统一，避免学生 / 导师 / 企业三套完全不同结构。

角色差异主要体现在：

- 顶部壳层
- 返回工作台入口
- 业务动作 CTA 的实际目标页

### 5.4 用户文案优先，技术文案后置

正式 UI 中不应默认直接展示：

- `payload`
- `refType`
- `refId`
- `actionCode`
- `WebSocket`
- `ACK`

页面文案应使用业务语言，例如：

- `实时提醒正常`
- `桌面提醒已开启`
- `关联订单`
- `关联任务`
- `继续处理`

### 5.5 偏好设置不应抢占主工作区

通知中心的主任务是“看消息与继续处理”，不是“频繁改通知设置”。

因此偏好设置应作为：

- 顶部入口
- 右侧二级面板
- 抽屉
- 折叠区

而不应长期与通知详情并列占据首屏主要注意力。

## 6. 正式信息架构

页面正式采用 `顶部概览层 + 主工作区` 的两层结构。

### 6.1 顶部概览层

顶部概览层必须回答“这里是什么页、现在整体情况如何、我有哪些快速动作”。

建议包含：

- 页面标题：`通知中心`
- 一句副标题：强调“统一查看平台消息并继续处理业务”
- 返回工作台入口
- 同步刷新入口
- 全部标记已读
- 桌面提醒入口
- 设置入口

### 6.2 概览摘要区

概览摘要区用于快速传达通知健康度与待办密度，建议使用 3 到 4 张摘要卡。

首版推荐字段：

- 未读总数
- 今日新增或最近一段时间新增
- 待处理 / 高优先级数量
- 提醒状态摘要

说明：

- 其中“提醒状态摘要”可以是实时同步状态和桌面提醒状态的组合表达
- 不要求把技术连接状态做成大面积主视觉

### 6.3 主工作区

宽屏桌面端下，主工作区推荐采用左右分栏：

1. 左侧：筛选 + 列表
2. 右侧：通知详情

偏好设置建议作为：

- 右侧详情区的次级标签页
- 独立设置抽屉
- 页面右上角设置按钮呼出的侧栏

不建议做成“列表、详情、设置三栏同时常驻”的结构，否则会分散主任务注意力。

## 7. 页面必须具备的功能模块

### 7.1 顶部头部与快捷操作

头部必须提供：

- 页面标题与页面说明
- 返回当前角色工作台
- 同步刷新
- 全部标记已读
- 桌面提醒授权 / 状态入口
- 通知设置入口

可选增强：

- 最近同步时间
- 简洁的实时状态提示

### 7.2 筛选导航

筛选导航至少应支持：

- `全部`
- `仅未读`
- 分类筛选

通知分类首版至少覆盖：

- AI 任务
- 咨询订单
- 悬赏任务
- 认证审核
- 系统公告
- 社区互动

可选增强但非首版必需：

- 仅待处理
- 仅高优先级
- 时间范围
- 本地关键词搜索

### 7.3 通知列表

通知列表必须是页面主区块之一，承担“快速浏览 + 判断优先级 + 选择一条查看详情”的职责。

每条列表项建议包含：

- 未读状态
- 分类标签
- 标题
- 一行到两行摘要
- 时间
- 主要动作提示
- 高优先级提示

不建议在列表项里堆叠过多字段，例如：

- 大量技术标识
- 冗长说明文
- 多层统计数字

### 7.4 通知详情

详情区是通知中心的第二主区块，承担“解释这条通知为什么出现、我现在能做什么”的职责。

详情区必须包含：

- 标题
- 完整摘要
- 状态标签
- 创建时间
- 来源模块
- 主要 CTA
- 次级动作，例如标记已读

详情区应优先展示“业务上下文”，例如：

- 关联订单
- 关联任务
- 关联帖子
- 关联认证流程
- 最近动作说明

不应把原始技术字段直接作为正式内容主呈现。

如果当前后端只提供结构化字段与 payload，则前端应尽量做业务翻译层，把能翻译成业务语义的内容转成用户可读信息，再决定是否保留少量补充信息。

### 7.5 通知设置

通知设置应包含以下能力：

- 站内收件箱开关说明
- 实时提醒开关
- 桌面提醒开关
- 邮件通知开关
- 邮件优先级阈值

设置区还应提供：

- 浏览器桌面提醒授权状态说明
- 当前类别说明
- 权限被浏览器拦截时的引导文案

设置区的文案必须偏产品表达，不要写成技术配置表。

## 8. 列表项设计规则

### 8.1 信息层级

列表项的信息层级应固定为：

1. 状态与分类
2. 标题
3. 摘要
4. 时间 / 动作提示

### 8.2 未读表达

未读表达建议使用以下组合：

- 红点或强调圆点
- 更高对比度标题
- 轻量状态标签

已读表达应收敛，不需要继续抢视觉焦点。

### 8.3 优先级表达

高优先级和紧急通知允许高亮，但不应导致整个列表过度红色化。

建议：

- 常规通知保持中性样式
- 高优先级使用少量强调色
- 紧急通知使用更明确色彩或标签

### 8.4 选择态

选中态必须明显，让用户一眼知道右侧详情正在对应哪一条通知。

## 9. 详情区设计规则

### 9.1 正确职责

详情区的核心职责是：

- 解释通知内容
- 展示上下文
- 给出下一步动作

### 9.2 必备元素

详情区建议包含：

- 通知标题
- 业务摘要
- 状态标签
- 时间
- 来源模块
- 主按钮：继续处理 / 查看详情 / 回到原页面
- 次按钮：标记已读

### 9.3 降级规则

当通知没有可直达目标时：

- 主按钮应禁用或降级为解释按钮
- 必须明确告诉用户“当前没有可直达页面”
- 不允许点击后静默无响应

### 9.4 技术信息展示边界

正式产品中，以下内容不应默认大面积展示：

- 原始 payload 键值
- 内部枚举码
- 原始链路标识

如确有必要，可作为：

- 折叠的“补充信息”
- 开发态调试信息
- 非首屏的附属说明

## 10. 设置与权限交互规则

### 10.1 浏览器桌面提醒

页面必须清楚区分以下状态：

- 未授权
- 已授权
- 被浏览器阻止
- 当前环境不支持

### 10.2 权限引导

当用户尝试开启桌面提醒时：

- 若尚未授权，应触发授权流程
- 若已被阻止，应提示用户去浏览器设置中重新开启
- 若当前环境不支持，应明确说明限制

### 10.3 设置区展示方式

设置区不应像后台配置页一样铺满首屏。

更合理的方式是：

- 顶部“通知设置”入口
- 打开右侧抽屉或浮层
- 在设置面板内按分类查看与调整

## 11. 实时与离线状态表达

### 11.1 实时状态应该被看见，但不该喧宾夺主

通知中心需要让用户感知：

- 当前是否正常同步
- 是否需要重新刷新

但不建议把技术连接状态做成 Hero 区最核心的大标题。

### 11.2 推荐表达方式

推荐使用用户能理解的业务文案，例如：

- `实时提醒正常`
- `正在恢复同步`
- `当前已切换为收件箱补偿模式`
- `桌面提醒已开启`

避免直接把 `WebSocket`、`WS` 作为主要产品文案。

### 11.3 新通知到达时的页面反馈

当实时新通知进入时，页面应：

- 未读数即时更新
- 当前筛选命中时列表顶部插入
- 不强制打断用户当前阅读
- 对新到消息给予轻量高亮

## 12. 空态 / 加载 / 错误态

### 12.1 加载态

通知中心应提供骨架屏，而不是简单的“加载中”文本。

建议覆盖：

- 列表加载
- 详情加载
- 设置加载

### 12.2 空态

至少需要覆盖以下空态：

- 当前没有任何通知
- 当前筛选条件下没有结果
- 当前没有未读通知
- 当前没有可配置偏好数据

空态文案应鼓励用户理解页面，而不是显示技术占位语。

### 12.3 错误态

错误态至少应支持：

- 列表拉取失败
- 设置拉取失败
- 偏好保存失败
- 连接异常后的重试提示

错误态必须配合明确的重试动作。

## 13. 文案与视觉要求

### 13.1 文案要求

通知中心必须坚持中文业务文案：

- 使用“通知中心”“继续处理”“桌面提醒”“实时提醒”等表达
- 不使用过多技术术语
- 不直接暴露内部英文枚举和值

### 13.2 视觉方向

整体视觉应符合“工作台中的消息中心”而不是“系统后台控制台”。

关键词：

- 清晰
- 稳定
- 可快速决策
- 信息密度适中
- 操作优先

### 13.3 页面密度控制

通知中心不是展示型首页，不需要过度拉高 Hero 区。

更合理的密度策略是：

- 头部简洁
- 摘要卡适度
- 列表为主
- 详情明确

## 14. 首版必须具备与后续预留

### 14.1 首版必须具备

- 统一通知中心路由
- 顶部统一操作区
- 未读 / 全部切换
- 分类筛选
- 列表 + 详情双区结构
- 单条已读
- 全部已读
- 实时状态表达
- 桌面提醒授权入口
- 分类通知偏好
- 稳定 deep-link 与降级说明

### 14.2 后续预留

- 搜索
- 归档
- 恢复未读
- 安静时段编辑
- 更智能的待处理聚合
- 批量处理
- 更细粒度的跨设备提醒策略

## 15. 验收标准

1. 用户首次进入 `/notifications` 时，首屏能同时看懂“有多少消息”“哪些值得优先处理”“接下来能做什么”。
2. 页面结构以“列表 + 详情”为核心，不被设置区或技术状态区抢占主要空间。
3. 学生、导师、企业三个角色都能复用同一通知中心主体骨架，只在回跳和业务动作目标上做角色差异。
4. 重要通知能够通过未读状态、优先级和动作提示快速识别。
5. 详情区展示的是业务上下文，而不是原始技术字段。
6. 当通知没有可直达目标时，页面能明确说明原因并优雅降级，不出现静默无响应。
7. 页面能清楚表达桌面提醒授权状态与实时同步状态，但不把技术术语作为主视觉语言。
8. 偏好设置可访问、可理解、可修改，但不会长期压过通知阅读与处理主任务。
