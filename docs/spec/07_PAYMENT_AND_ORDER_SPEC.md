# 支付与咨询订单规范

> **文档状态**：`evolving` · 最后审核：2026-03-24 · 状态机已定，回调与异常处理细节可能随实现调整。
>

## 1. 目标与范围
定义咨询订单生命周期、支付双轨策略、沙箱接入流程、回调幂等与异常处理。

## 2. 订单领域模型
核心字段：
- `orderNo`
- `studentUserId`
- `mentorUserId`
- `amountFen`
- `status`
- `sceneCode`
- `questionText`
- `questionPayload`
- `prepSheetSnapshot`
- `appointmentStartAt`
- `appointmentEndAt`
- `paidAt`
- `closedAt`

状态集合：
- `CREATED`
- `PAYING`
- `PAID`
- `ANSWERED`
- `CLOSED`
- `FAILED`
- `CANCELED`
- `REFUNDED`

### 2.1 正式订单创建页输入快照
- 学生端正式订单创建页不应只提交一段自由文本，而应保留结构化问题输入快照。
- 推荐至少保存以下结构：
  - `primaryConcern`
  - `background`
  - `attemptedActions`
  - `expectedHelp`
  - `additionalNotes`
- `questionText` 仍保留为订单主问题文本，用于兼容当前最小链路、搜索、通知与消息线程引用。
- `prepSheetSnapshot` 用于承接导师广场准备单导入结果，避免推荐页与下单页上下文断裂。

### 2.2 咨询材料包语义
- 正式订单创建页应允许学生上传多文件材料包。
- 材料包需区分“单槽位材料”和“多槽位材料”：
  - 单槽位：如简历、岗位 JD，同一时刻默认只保留最新有效副本。
  - 多槽位：如项目材料、Offer 材料、补充材料，可并存多份当前有效材料。
- 当前前台不要求文件预览，也不要求显式版本管理页。
- 即使前台不展示版本历史，系统内部仍应保留被替换材料的 `SUPERSEDED` 留痕。

## 3. 状态机规则
主路径：
1. 下单后 `CREATED`
2. 发起支付后 `PAYING`
3. 回调成功后 `PAID`
4. 导师答复后 `ANSWERED`
5. 完成后 `CLOSED`

异常路径：
- `FAILED`：支付初始化失败
- `CANCELED`：支付前取消
- `REFUNDED`：退款（v1 先支持管理员后台手工退款/售后，不接真实支付网关原路退回）

约束：
- `CREATED -> PAYING` 仅一次。
- 未 `PAID` 不允许导师进入付费答复流程。
- 非法流转返回 `BIZ-1002`。

## 4. 支付双轨策略
### 4.1 主路径：支付宝沙箱
- 用于真实支付演示。
- 需要沙箱商户配置与回调地址。

### 4.2 回退路径：模拟支付
- 通过开关 `payment.mode=MOCK` 启用。
- 模拟成功事件但保留完整审计。
- 不得绕过订单状态校验。

### 4.3 运行时切换
- 管理员可切换支付模式。
- 切换动作写审计日志。
- 进行中的订单保持原模式处理。

## 5. 沙箱接入步骤
1. 配置 `app_id`、私钥、公钥。
2. 实现支付发起接口，生成支付链接/表单。
3. 写入支付初始化记录（`INIT`）。
4. 接收异步回调。
5. 验签并校验金额。
6. 幂等更新状态。
7. 返回支付平台要求的成功应答。

## 6. 回调验签与幂等
必须校验：
- 签名
- 订单存在
- 金额匹配
- 交易状态为成功

幂等设计：
- 幂等键：`provider_trade_no`
- 唯一索引：`payment_records.idempotency_key`
- 重复回调只返回成功确认，不重复变更业务状态。

事务步骤：
1. 锁定订单行。
2. 校验当前状态可支付。
3. 写支付记录。
4. 更新订单至 `PAID`。
5. 写审计日志。
6. 提交事务。

## 7. 咨询消息规则
- 学生可在订单中提问。
- 导师“服务答复”要求订单已支付。
- 导师答复后订单状态进入 `ANSWERED`。
- 学生确认问题解决后，显式调用关单接口把 `ANSWERED` 置为 `CLOSED`。
- 订单进入 `CLOSED` 后，学生可提交一次咨询评价（1-5 星 + 可选文字），评价写入 `consult_reviews` 表，并汇总更新 `mentor_profiles.avg_rating`。每个订单仅允许一次评价（`order_no` 唯一约束保证）。
- 学生在聊天过程中若补充或替换材料，系统应产生可见事件提示，例如“学生已更新简历”。
- 导师前台默认只查看当前有效材料包，不要求在聊天流中手动辨认旧版本文件。

## 7.1 未支付订单取消 / 超时回收
- 学生可主动取消 `CREATED` 或 `PAYING` 且仍未支付的订单，订单状态置为 `CANCELED`。
- v1 默认未支付超时阈值为 30 分钟，可通过 `payment.unpaid-timeout-minutes` 调整。
- 超时回收采用“定时任务 + 懒检查”双保险：后台定时扫描超时订单，列表/详情/支付前也会懒触发回收。
- 订单列表/详情响应应返回 `autoCancelAt`，供前端展示倒计时与“自动取消时间”；详情页在 `CREATED/PAYING` 阶段可定时轮询以感知支付回调后的状态变化。
- 若订单预占了导师排期时段，则取消或超时回收时同步释放该时段（`BOOKED -> AVAILABLE`）。
- 超时取消事件可继续补审计日志；当前先保证状态与排期一致性。

## 8. 异常单处理
### 8.1 支付初始化失败
- 订单置 `FAILED`。
- 保存失败原因。

### 8.2 回调验签失败
- 拒绝回调并记录安全日志。
- 不改订单状态。

### 8.3 金额不一致
- 记录异常，保持原状态并进入人工核查。

### 8.4 回调重复
- 幂等返回，不重复记账。

### 8.5 导师超时未答
- v1 已改为“系统自动售后退款”策略，而非纯人工介入。
- 触发条件：订单仍处于 `PAID`，且从 `paidAt` 起超过 `consult.mentor-reply-timeout-hours` 后导师仍未正式答复。
- 处理方式采用“定时任务 + 懒检查”双保险：后台按 `consult.mentor-reply-reclaim-fixed-delay-ms` 周期扫描，订单列表/详情读取时也会顺带检查。
- 若该订单已有 `PENDING` 售后申请，系统会直接审批通过；若没有，则自动创建一条 `auto_triggered=true` 的退款售后申请并立即审批通过。
- 自动处理最终复用统一退款逻辑：订单状态更新为 `REFUNDED`，写入审计日志，并向学生/导师发送站内通知。

### 8.6 管理员手工退款 / 售后
- v1 已补齐最小“完整售后链”：`学生发起售后申请 -> 管理员审核通过/驳回 -> 审核通过时执行统一退款逻辑`。
- 仍保留管理员后台手工退款入口，作为无申请单场景下的兜底处理方式。
- 仅允许处理 `PAID`、`ANSWERED`、`CLOSED` 订单；处理后订单状态置为 `REFUNDED`。
- 若预约时段尚未结束，则同步释放该时段；若订单已关闭且已评价，则移除评价并刷新导师评分与完成单数。
- 售后申请、审核结果与退款说明会分别写入售后表/审计日志，并向学生/导师发送站内通知。
- 导师超时未答自动退款同样复用这条统一退款收口逻辑，只是审核人由系统扮演，且申请单会标记 `auto_triggered=true`。
- 当订单最近一次支付模式为 `SANDBOX` 且存在成功支付记录时，管理员退款会先调用 `alipay.trade.refund` 发起全额退款；沙箱限制为“每笔订单只允许调用一次退款接口，且退款金额必须等于支付金额”。
- 退款后可继续通过 `alipay.trade.fastpay.refund.query` 查询沙箱退款状态；未支付 `SANDBOX` 订单则可通过 `alipay.trade.close` 主动关单。
- `MOCK` 或缺失有效沙箱支付成功记录的订单，仍按平台内逻辑退款收口。
- 口径说明：本节中的“退款完成”首先表示平台内订单、售后与审计状态已收口；是否已经发生外部资金原路退回，还需结合 `refund.query` 结果或后台人工确认动作单独判断。

### 8.6.1 沙箱交易查询 / 关单 / 退款查询
- 管理员订单页支持对 `SANDBOX` 订单执行 `trade.query / trade.close / refund.query` 三类动作。
- `trade.query` 发现外部已支付成功而本地仍停在 `PAYING` 时，会自动补记本地支付成功。
- `trade.close` 仅允许作用于 `CREATED/PAYING` 且未支付订单；成功后本地同步取消并释放已预占资源。
- `refund.query` 固定使用 `REFUND-{orderNo}` 作为退款请求号，便于与本地审计和支付记录对齐。

### 8.7 支付对账 / 异常单人工处理
- v1 新增管理员“平台内对账台”，用于比对 `consult_orders`、`payment_records` 与人工审计记录是否一致。
- 当前对账范围为**平台内对账**，不直接拉取支付宝官方账单文件；重点解决毕设演示中的“回调漏落单、未支付挂起、逻辑退款后的外部退款确认”三类问题。
- 对账结果建议口径：
  - `MATCHED`：订单状态与支付记录口径一致；
  - `PENDING`：订单仍处正常待支付阶段；
  - `REVIEW_REQUIRED`：存在需要管理员处理的异常；
  - `REVIEWED_PENDING`：管理员已登记核对，但异常仍待进一步跟进；
  - `MANUALLY_RESOLVED`：管理员已通过人工动作把当前异常单收口。
- 当前人工动作：
  - `MARK_PAID`：将“已收到成功支付记录但订单仍停在 `PAYING/CREATED`”的异常单补记为 `PAID`；
  - `CANCEL_UNPAID`：将长时间挂起的未支付异常单取消并释放预约资源；
  - `CONFIRM_EXTERNAL_REFUND`：在 `REFUNDED + SANDBOX` 场景下登记“外部退款已人工确认完成”；
  - `MARK_REVIEWED`：只登记人工核对备注，不改业务状态。
- 所有人工动作必须写入 `audit_logs`，并在必要时给学生/导师发送站内通知。
- 边界说明：支付对账页当前是“平台内对账与异常单处理台”，重点核对本地订单、支付记录与人工处理状态，不等同于直接拉取支付宝官方账单后的财务级对账。

## 9. 模拟支付审计要求
模拟支付触发时必须记录：
- 操作人
- 订单号
- 触发原因
- 状态前后变化
- 时间戳

## 10. 安全要求
- 回调接口必须验签。
- 密钥不可硬编码。
- 回调原始载荷可审计留档。

## 11. 测试要求
1. 下单到支付成功主路径。
2. 重复回调幂等。
3. 无效签名拒绝。
4. 沙箱/模拟模式切换。
5. 导师答复状态前置校验。

## 12. 本文档范围
覆盖 v1 咨询订单与支付、正式订单创建页输入快照、咨询材料包规则，以及管理员手工退款/售后最小闭环；不覆盖完整退款申请/审批、原路退回与改签流程，也不覆盖前台文件预览和显式版本管理中心。

## 13. 决策摘要
- 双轨支付必保留。
- 幂等与审计为强制约束。

## 14. 验收标准
1. 沙箱与模拟模式都可运行。
2. `PAID` 仅成功写入一次。
3. 订单闭环可现场演示。
4. 状态流转可追踪可审计。
