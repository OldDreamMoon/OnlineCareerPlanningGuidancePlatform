# 测试计划

> **文档状态**：`evolving` · 最后审核：2026-04-18 · 用例矩阵已按当前已部署实现回写；本文用于论文描述“测试覆盖范围与验证策略”，不等同于最新一轮完整人工回归报告。
>

## 1. 测试范围
- 单元测试：服务逻辑、状态流转、参数校验。
- 集成测试：数据库、AI 模块适配、支付回调。
- 端到端测试：关键用户旅程。
- 非功能测试：基础性能与稳定性。

补充说明：
- 当前项目已形成“自动化集成测试 + 定向构建验证 + 关键业务人工浏览器回归”的组合测试策略。
- 论文口径下，本文强调“测试设计与覆盖面”；某条用例是否完成最新一轮人工真环境回归，仍应结合 [`13_ACCEPTANCE_CHECKLIST.md`](docs/spec/13_ACCEPTANCE_CHECKLIST.md) 与实际验收记录判断。

## 2. 测试环境
- Linux + Docker Compose
- 可控种子数据
- 可用测试凭据：AI、支付沙箱，以及在启用正式注册校验时可用的 Geetest / Resend 配置
- 浏览器端测试环境需支持 WebSocket 建连与 Notification API 授权

## 3. 测试类型与分工
- Java 后端：单元/集成
- AI 模块：契约/适配/回退
- 前端：路由鉴权与核心页面
- E2E：答辩脚本链路

## 4.1 测试数据策略
种子数据最小集：
- 账号：每个角色至少 1 个测试账号（共 4 个），密码统一为 `Test1234!`。
- 技能树：至少 5 个节点，含前置关系。
- 社区：至少 3 个帖子，含 1 个已有 AI 回答。
- 导师：至少 1 个已审核通过、可接单的导师。
- 企业：至少 1 个已发布的悬赏任务。
- AI 配置：至少 1 个激活的提供商与模型路由。
- 支付：沙箱配置可用或已切换为 MOCK 模式。
- 注册验证：若启用正式注册链路，需准备可用的 Geetest captchaId/captchaKey 与 Resend API Key/发件邮箱。
- 内容治理：至少 10 条敏感词（含白名单），至少 2 条审查策略，至少 3 条测试举报数据。
- 画像：至少 3 名学生具备不同技能进度/问答/社区行为样本。
- 榜单：至少 20 条近 7 天社区互动事件，含跨窗口历史样本（>7天）。

## 5. 回归清单
- JWT 与刷新机制
- RBAC 拦截
- 订单状态机
- 支付幂等与验签
- 正式注册验证链路（`Geetest -> /auth/email/send-code -> /auth/email/verify-code -> emailVerificationToken`）
- 积分一致性
- AI trace 与日志
- 社区审核可见性
- 审查结果可追溯（`content_moderation_events`）
- 举报状态与处置流水一致（`content_reports` + `content_report_actions`）
- 画像快照一致性（`student_portrait_snapshots`）与证据可解释性
- 社区贡献榜排序稳定性与窗口边界正确性
- 通知偏好、WS ticket、ACK 回执与离线补偿一致性

## 6. 性能与稳定性最低目标
- 非 AI 接口 p95 < 500ms
- AI 接口 p95 < 6s（外部故障除外）
- 支付回调在重复通知下稳定
- 并发下无数据破坏

## 7. 故障注入测试
1. 强制 AI 超时，验证回退。
2. 关闭沙箱，验证模拟支付。
3. 重复同一回调 3 次，验证幂等。
4. Redis 异常时验证可控降级。
5. 审查引擎不可用时验证开关降级与补偿审计。

## 8. 答辩脚本测试
- 脚本1：注册（Geetest + 邮箱验证码） + 简历优化 + 文本面试 + 面试总结报告
- 脚本2：AI 简历异步提交 -> 离开页面 -> 通知触发 -> 结果页回看
- 脚本3：下单 + 支付 + 导师答复 + 通知触发 + 评价
- 脚本4：企业任务发布与提交审核
- 脚本5：语音最小闭环
- 脚本6：敏感输入拦截 + 社区待审 + 举报 + 管理员处置
- 脚本7：学生冷启动画像 -> 社区互动 -> 画像刷新 -> 企业任务内筛选命中 -> 社区榜单展示
- 脚本8：`live` 实时语音测试模式 -> transcript 回灌 -> summary -> AI 复盘中心回看

通过标准：7 个脚本均可无人工补丁演示。

## 9. 准入与退出标准
### 准入
- 核心接口开发完成
- 种子数据可用
- 环境变量配置正确

### 退出
- P0 与 P1 关键测试通过
- P2 语音至少成功一次
- 无未解决 P0 阻塞缺陷

## 10. 缺陷分级
- P0 阻塞：影响核心演示链路
- P1 重大：影响支付或业务闭环
- P2 次要：不影响主链路

发布规则：存在未解决 P0 阻塞则禁止发布。

## 11. 测试目标
- 覆盖论文中需要展示的核心闭环：注册认证、AI 求职辅助、成长积分、社区互动、导师咨询、企业悬赏、通知治理与部署回归。
- 覆盖项目收尾阶段的关键风险点：部署口径一致性、支付双轨、`live` 测试模式边界、内容治理降级与回滚路径。

## 12. 决策摘要
- 关键闭环优先于边缘功能。
- 回退路径必须纳入测试而非仅文档声明。
