## 3. 当前冻结的总体决策
### 3.1 持久层路线
当前冻结主路线为：

- 主业务持久层：`Spring Data JPA + Hibernate`
- 不再继续扩张新的 `JdbcTemplate + 显式 SQL`
- pilot 期默认不新增 native SQL；若个别仓储因 PostgreSQL / H2 兼容性必须豁免，只允许保留极小范围例外并同步登记 `change_request_log.md`

### 3.2 测试路线
当前冻结测试路线为：

- H2 保留为历史兼容测试基线，不再作为 PostgreSQL 迁移正确性的主依据
- 新增 PostgreSQL Testcontainers 作为数据库集成测试主基线
- pilot 域相关集成测试必须率先切到 PostgreSQL Testcontainers

### 3.3 Flyway 路线
当前冻结 Flyway 路线为：

- MySQL 旧链路保持只读冻结，不在当前迁移阶段继续改造为 PostgreSQL 兼容脚本
- PostgreSQL 建立单独的新 migration 目录和新基线
- pilot 域的 PostgreSQL schema 只在 PostgreSQL 新链路里表达，不回写到 MySQL migration

## 4. PostgreSQL 全局建模约定
### 4.1 表与命名
- 表名继续使用 `snake_case`，与现有数据库命名保持一致。
- 列名继续使用 `snake_case`，避免在 pilot 期同时改数据库命名风格。
- Java 实体与字段使用驼峰命名，通过 JPA 注解映射到 `snake_case`。
- pilot 期不做表名重命名，不借 ORM 引入命名大扫除。

### 4.2 主键与唯一约束
默认规则：

- 对“新建或重建的主事实表”优先使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`。
- 对当前已经稳定使用自然键的表，不在 pilot 期强行改成自增主键。
- 所有历史唯一约束必须显式保留，不能仅靠代码侧逻辑兜底。

技能域 pilot 例外冻结如下：

- `skills.node_code` 继续作为自然主键，不改为 `BIGINT`。
- `skill_node_resources.resource_code` 继续作为自然主键，不改为 `BIGINT`。
- `skill_progress.id`、`skill_relations.id` 继续使用数值主键，并保留原有唯一约束：
  - `uq_skill_progress_user_node`
  - `uq_skill_relations_unique`

### 4.3 时间类型
全局冻结规则：

- PostgreSQL 基线默认使用 `TIMESTAMPTZ` 表达应用时间。
- Java 侧统一映射为 `Instant`。
- 不再为新链路保留“本地时区时间 + 应用层约定解释”的做法。
- 排序、保留期、失效时间、重试时间一律以 UTC 语义处理。

### 4.4 布尔与枚举
- MySQL 中的 `TINYINT(1)` 在 PostgreSQL 基线中统一评估为 `BOOLEAN`。
- 枚举字段在第一阶段继续使用 `VARCHAR` + Java `enum` 映射，不引入 PostgreSQL enum。
- 只有在某一域的值域长期稳定、跨服务共享且变更极少时，才允许后续专项评估 PG enum。

### 4.5 JSON 与长文本
- 所有“上下文快照 / payload / extra config / 结果摘要”类字段在 PostgreSQL 中默认使用 `JSONB`。
- 长文本默认使用 `TEXT`。
- pilot 域技能表当前不引入 JSONB，因为其结构化关系已经以正规表表达。

### 4.6 审计字段
- `created_at`、`updated_at` 统一保留。
- Java 实体默认使用 `@PrePersist` / `@PreUpdate` 或等价审计机制维护时间字段。
- 不在 pilot 期引入过重的审计框架，只做最小可维护实现。

### 4.7 关联与抓取策略
- 所有关联默认 `LAZY`，禁止在 pilot 期因为偷懒把关联全部改成 `EAGER`。
- Controller 层禁止直接暴露实体，仍通过 DTO / response assembler 输出。
- 不依赖 Open Session in View 解决懒加载问题，统一在 service 层完成读取与组装。
- 因此在 JPA 引入阶段同步关闭：`spring.jpa.open-in-view=false`。

### 4.8 查询策略
当前冻结优先级如下：

1. Spring Data 派生查询方法
2. 基于实体关系的装配读取
3. JPQL / projection
4. native query 作为临时豁免，仅在无法用前三者表达时才允许

额外约束：

- pilot 域默认不引入 native query；当前仅允许像 [`GrowthCheckinJpaRepository.java`](apps/server-java/src/main/java/com/bishe/server/growth/repository/jpa/GrowthCheckinJpaRepository.java) 这样经 H2/PG 双验证确认、因 `DATE` 绑定差异而必须显式 `CAST(:date AS DATE)` 的极小范围受控例外。
- 若后续某域必须使用 native query，必须登记到 `change_request_log.md`，并附带“为什么不能由实体关系或 JPQL 承接”的说明，以及“回收该例外的触发条件”。
- 不再新增 `JdbcTemplate` 仓储作为“临时过渡方案”。

### 4.9 事务与锁
- pilot 域优先采用普通事务边界，不提前引入悲观锁；若必须保留旧 JDBC 的单行 `FOR UPDATE` 语义，只允许在单仓储内以 JPA 锁注解做最小替代，并同步登记例外。
- 后续咨询/支付等强一致域若需要 `FOR UPDATE` 语义，统一通过 JPA 锁注解或数据库专用策略单独设计。
- 不把支付/售后域的锁策略外推到技能域。

## 5. Maven 与运行配置冻结建议
### 5.1 Maven 依赖新增清单
当开始代码级 pilot 时，后端 `pom.xml` 需要最小新增以下依赖：

- 运行时：
  - `org.springframework.boot:spring-boot-starter-data-jpa`
  - `org.postgresql:postgresql`
  - `org.flywaydb:flyway-database-postgresql`
- 测试：
  - `org.springframework.boot:spring-boot-testcontainers`
  - `org.testcontainers:junit-jupiter`
  - `org.testcontainers:testcontainers-postgresql`

同时保留：

- `spring-boot-starter-jdbc`
- `flyway-core`
- `flyway-mysql`
- `mysql-connector-j`

原因：

- pilot 阶段仍需维持旧 MySQL migration / H2 兼容链路与部分历史运维工具的可编译状态。
- 当前默认 runtime 虽已切到 PostgreSQL，但不能在同一批里直接删除 JDBC/MySQL 依赖，否则会把“技能域试点”扩张成“全项目依赖清理 + 历史工具迁移”的混合大专题。

### 5.2 Spring 配置冻结建议
PostgreSQL 主链路默认采用以下约定：

- `spring.jpa.hibernate.ddl-auto=validate`
- `spring.jpa.open-in-view=false`
- `spring.sql.init.mode=never`
- 通过 Flyway 初始化 PostgreSQL schema，而不是通过测试 `schema.sql`
- 不显式硬编码 Hibernate dialect，优先交给驱动自动识别

当前本地开发入口已同步具备以下显式运行方式：

- `bash scripts/dev/05_start_apps_local.sh`
- `bash scripts/dev/05_start_apps_local.sh --postgres`
- `cd apps/server-java && SPRING_PROFILES_ACTIVE=postgres DB_URL=jdbc:postgresql://127.0.0.1:5432/bishe DB_USERNAME=bishe DB_PASSWORD=bishe mvn -Dmaven.repo.local=/home/olddream/.cache/dev/maven/repository -DskipTests spring-boot:run`

以上命令中的无参一键入口已经默认走 PostgreSQL；显式 `--postgres` 与手工 `SPRING_PROFILES_ACTIVE=postgres` 主要用于强调目标运行态和绕过本地遗留环境变量。

## 6. Flyway PostgreSQL 新基线方案
### 6.1 新目录策略
当前推荐：

- 保留现有 MySQL migration 目录不动
- 新增 PostgreSQL 专用目录，例如：
  - `apps/server-java/src/main/resources/db/migration-pg`

并通过 profile / 配置切换：

- MySQL 链路：继续使用现有 MySQL migration 目录
- PostgreSQL 链路：显式指向 `classpath:db/migration-pg`

### 6.2 为什么不直接复用旧目录
当前不建议直接在旧目录上“边改边兼容 PostgreSQL”，原因是：

- 现有 69 份 migration 已深度携带 MySQL 方言
- 直接在原目录双向兼容会让每一份历史 migration 都变成条件分支点
- pilot 需要的是“从空 PostgreSQL 库可稳定重建技能域”，而不是“让旧链路半兼容”

### 6.3 新基线最小骨架
当前建议 PostgreSQL 新链路优先覆盖：

1. `S0` 系统基线
2. `S1` 平台基础配置
3. `A1` 账号主干
4. `B2` 技能域 pilot

理由：

- 技能域依赖 `users`
- 不需要等待咨询/支付/通知/AI 域完成，便可独立验证 ORM 路线

## 7. PostgreSQL Testcontainers 测试方案
### 7.1 新测试分层
当前建议把测试分成两层：

- `legacy-h2`：保留当前 `@ActiveProfiles("test")` 的 H2 测试，作为旧链路兼容参考
- `postgres-integration`：新建 PostgreSQL Testcontainers 基线，用于 pilot 域与后续迁移域

### 7.2 Profile 策略
当前建议新增：

- `application-test-postgres.yml`

其职责：

- 开启 Flyway
- 关闭 `schema.sql` 初始化
- 配置 JPA / Hibernate 相关开关
- 保留与 `application-test.yml` 共享的 JWT / mock 第三方配置

当前不建议直接覆写 `application-test.yml`，原因是：

- 全量替换会一次性影响当前 34 个 H2 测试类
- pilot 需要的是“并行引入 PostgreSQL 测试”，而不是“先把旧测试体系打断”

### 7.3 容器启动方式
当前推荐采用：

- `@Testcontainers`
- `@Container`
- `@ServiceConnection`
- `PostgreSQLContainer`

再叠加一个统一基类或元注解，例如：

- `AbstractPostgresIntegrationTest`
- 或 `@PostgresIntegrationTest`

这样可以把以下行为集中收口：

- 容器镜像版本
- 容器生命周期
- Flyway 初始化方式
- 测试 profile 组合

### 7.4 测试迁移顺序
当前建议按以下顺序迁移测试：

1. 技能域测试
   - [`SkillTreeIntegrationTest.java`](apps/server-java/src/test/java/com/bishe/server/profile/SkillTreeIntegrationTest.java)
   - [`AdminSkillOpsIntegrationTest.java`](apps/server-java/src/test/java/com/bishe/server/skill/AdminSkillOpsIntegrationTest.java)
   - [`SkillNodeCacheServiceTest.java`](apps/server-java/src/test/java/com/bishe/server/skill/SkillNodeCacheServiceTest.java)
2. 与技能画像联动的学生资料测试
3. 再扩展到其他业务域

### 7.5 Testcontainers 通过标准
pilot 测试切换完成后，至少需要满足：

- 技能树查询接口在 PostgreSQL 下通过
- 技能进度更新接口在 PostgreSQL 下通过
- 管理员技能治理的增删改查在 PostgreSQL 下通过
- Redis 缓存回填逻辑不依赖 H2/MySQL 方言

## 9. 技能域实体建模冻结建议
### 9.1 `SkillNodeEntity`
建议映射：

- 表：`skills`
- 主键：`nodeCode: String`
- 自关联：
  - `parent: SkillNodeEntity`
  - `children: Set<SkillNodeEntity>`
- 关联：
  - `resources`
  - `outboundRelations`
  - `inboundRelations`
- 字段：
  - `label`
  - `description`
  - `sortOrder`
  - `createdAt`
  - `updatedAt`

注意：

- 读取树时禁止直接把完整双向图序列化到接口层。
- service 层应按 DTO 装配，避免循环引用和过度抓取。

### 9.2 `SkillRelationEntity`
建议映射：

- 表：`skill_relations`
- 主键：`id: Long`
- 唯一约束：`(source_node_code, target_node_code, relation_type)`
- 关联：
  - `sourceNode`
  - `targetNode`
- 字段：
  - `relationType`
  - `label`
  - `sortOrder`
  - `createdAt`
  - `updatedAt`

### 9.3 `SkillNodeResourceEntity`
建议映射：

- 表：`skill_node_resources`
- 主键：`resourceCode: String`
- 关联：
  - `node`
- 字段：
  - `resourceType`
  - `title`
  - `sourceLabel`
  - `durationLabel`
  - `linkUrl`
  - `sortOrder`
  - `createdAt`
  - `updatedAt`

### 9.4 `SkillProgressEntity`
建议映射：

- 表：`skill_progress`
- 主键：`id: Long`
- 唯一约束：`(student_user_id, node_code)`
- 关联：
  - `studentUser` 只保留到 `UserEntity` 的轻关联
  - `node`
- 字段：
  - `progressStatus`
  - `updatedAt`

### 9.5 技能域特例说明
技能域是本项目里少数“同时存在自然键与数值键”的混合域：

- `skills` 和 `skill_node_resources` 以业务编码作为主键
- `skill_progress` 和 `skill_relations` 以数值主键承接写入

当前冻结结论是：

- pilot 期接受这种混合形态
- 不在 pilot 期同时做“全域统一改成 bigint 主键”的结构治理

## 10. 技能域 Repository 设计建议
### 10.1 Repository 划分
建议拆为两层：

- 基础实体仓储：
  - `SkillNodeJpaRepository`
  - `SkillRelationJpaRepository`
  - `SkillNodeResourceJpaRepository`
  - `SkillProgressJpaRepository`
- 领域装配服务：
  - 学生技能树读取装配
  - 管理员技能治理读取装配

### 10.2 为什么不把管理员聚合查询塞进一个巨型 `@Query`
当前 `AdminSkillOpsRepository` 的列表查询包含：

- 自关联父节点
- 子节点数量统计
- 资源数量统计
- 入边/出边数量统计

若直接把这类查询搬成单条复杂 JPQL，会带来两个问题：

- 仍然把“读取形状”硬编码成一个难维护的大查询
- 后续一旦 DTO 稍有变化，JPA 版本也会变成新的显式查询负担

当前推荐：

- 先用实体仓储读基础对象
- 再用批量计数仓储或 service 聚合组装后台列表
- 在 pilot 域接受“多次较小查询 + service 聚合”，而不是追求一步到位的大查询

### 10.3 技能域禁止项
pilot 域当前禁止：

- 新增 native SQL
- 新增 `JdbcTemplate` 临时补丁
- 直接返回实体给 controller
- 用 `EAGER` 关联掩盖 service 组装缺失

## 13. 风险与回滚
### 13.1 当前主要风险
- JPA 引入后若默认抓取策略处理不当，容易把技能树读取放大成 N+1 查询。
- 管理员技能治理列表若改造成“巨型 JPQL”，会从显式 SQL 问题变成显式查询问题。
- [`AiQuotaRepository.java`](apps/server-java/src/main/java/com/bishe/server/ai/quota/AiQuotaRepository.java) 当前只剩 `ai_call_logs`，但仍连接 quota、成本、路由命中与历史回放语义；若下一批直接并入，会把刚拆开的配置表 pilot 重新放大成日志型高风险批次。
- Growth 当前为了消除 H2 / PostgreSQL 在 `DATE` 绑定上的偏移，继续由 [`GrowthCheckinJpaRepository.java`](apps/server-java/src/main/java/com/bishe/server/growth/repository/jpa/GrowthCheckinJpaRepository.java) 保留极小范围 native SQL + `CAST(:date AS DATE)`，并让 [`UserAccountJpaRepository.java`](apps/server-java/src/main/java/com/bishe/server/auth/repository/jpa/UserAccountJpaRepository.java) 承接单行 JPA 悲观锁；该边界已在 H2/PG 双验证下确认为当前受控例外，不应向其他 pilot 域扩散。
- `ai_async_task_*` 当前已完成 JPA 仓储 pilot，并通过 [`V044__harden_ai_async_task_jsonb.sql`](apps/server-java/src/main/resources/db/migration-pg/V044__harden_ai_async_task_jsonb.sql) 把 `input_snapshot_json / context_json / prompt_snapshot_json / route_snapshot_json / result_payload_json / payload_json` 收口到 `JSONB`，同时以 [`AiAsyncTaskMaintenanceJob.java`](apps/server-java/src/main/java/com/bishe/server/ai/gateway/task/AiAsyncTaskMaintenanceJob.java) 补齐默认 30 天 retention；后续不应再把这个已完成专题误报为 active 例外。
- PostgreSQL 虽已在 `V041` 补齐咨询创单/消息/附件链路所需的 `consult_orders` 快照字段与 `consult_messages / consult_order_attachments`，并已支撑咨询复杂读查询收口，但后续若绕开现有基线、回退 schema 或把已完成专题返工与其他高耦合仓储混批，仍会重新放大 PostgreSQL 与 H2/MySQL 契约漂移风险。
- 治理域当前已通过 [`V043__harden_sensitive_terms_boolean_flags.sql`](apps/server-java/src/main/resources/db/migration-pg/V043__harden_sensitive_terms_boolean_flags.sql) 完成 `sensitive_terms.enabled / is_whitelist` 的 `BOOLEAN` 规范回收；后续若重新打开 Growth `DATE` 绑定例外评估并与新的高耦合仓储混批，仍会放大契约漂移风险。
- 多个 PostgreSQL `DataJpaTest` 类若在同一条 Maven 命令里串跑，可能在 `beforeTestMethod` 阶段命中 Hikari/Testcontainers 失效连接；当前应统一按“单类单命令”执行 PG 仓储测试。
- 导师排期仓储当前为保留“重复时段跳过继续”的旧语义，`createSlot` 使用了 `REQUIRES_NEW`；未来 PostgreSQL DataJpaTest 若在默认外层事务中准备 FK 依赖数据，仍可能出现数据不可见导致的 FK 假失败。
- PostgreSQL 基线若和当前 `schema.sql` 双轨漂移，测试结论会再次失真。

### 13.2 当前控制策略
- pilot 当前已扩到 auth/profile/skill/growth/mentor/notification/ai/admin/bounty/community 与完整治理域等多个已验证局部链路，其中 Growth、咨询售后、咨询支付/评价/审计辅助读写、咨询订单状态流转/超时扫描、咨询创单/消息/附件主链、咨询复杂读模型、导师推荐、导师财务中心、管理员导师经营台、导师主仓储、通知运营台、通知派发任务状态机、AI async jobs 状态机、悬赏主仓储、社区帖评赞、AI 历史/分析，以及治理域 `moderation_policies / sensitive_terms / content_reports / content_report_actions / content_moderation_events / audit_logs` 都已进入已验证集合。
